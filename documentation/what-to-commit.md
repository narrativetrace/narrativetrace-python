# What to commit

Everything NarrativeTrace writes today is a **generated artifact that describes one run** — there
is no reviewed baseline file in this runtime yet (the Java sibling's structural `.nt` format and its
approval-testing workflow are planned here, not shipped — see the
[Feature Guide](feature-guide.md)). Until that lands, the rule is simple: nothing under your
configured output directory is source, so none of it belongs in version control.

| Artifact | Path pattern | Commit? | Why |
|---|---|---|---|
| Trace file (Markdown, default format) | `<OUTPUT_DIR>/traces/<Class>/<slug>.md` | No | Regenerated every run |
| Trace file (`text`/`mermaid`/`plantuml` format) | `<OUTPUT_DIR>/traces/<Class>/<slug>.{txt,mmd,puml}` | No | Regenerated every run |
| JSON scenario document (Markdown format only) | `<OUTPUT_DIR>/traces/<Class>/<slug>.json` | No | Same trace as canonical JSON — regenerated every run |
| Mermaid diagram companion (Markdown format only) | `<OUTPUT_DIR>/diagrams/<Class>/<slug>.mmd` | No | Regenerated every run |
| Canonical entry array | `<OUTPUT_DIR>/traces/<Class>/<slug>.canonical.json` | No | A machine artifact for conformance/porting, opt-in via `NARRATIVETRACE_CANONICAL` |
| Suite clarity report | `<OUTPUT_DIR>/clarity-report.md` | No | A generated report, not a decision |
| Suite clarity results | `<OUTPUT_DIR>/clarity-results.json` | No | Generated alongside the report |
| Standalone scanner output (`narrativetrace-clarity` CLI) | wherever `--output-dir` points | No | Same as above, generated on demand |
| `glossary.json` / `glossary.md` | repository root (or wherever you point `NARRATIVETRACE_GLOSSARY_DIR`) | **Yes**, if you use it | Human-owned vocabulary — the committed file is what clarity scoring reads back, and it is never regenerated by a test run. "One file, one review workflow" |

The default `<OUTPUT_DIR>` is `narrative-traces` (relative to wherever the suite ran); add it to
your project's `.gitignore`:

```gitignore
narrative-traces/
```

If you point `NARRATIVETRACE_OUTPUT_DIR` somewhere else — a `build/` directory, a CI artifacts
folder — ignore that path instead. `glossary.json` is the one exception: it lives wherever you put
it (typically the repository root), is never written by a test run, and should be tracked like any
other source file.

## The rule in one sentence

If a file only exists because a test ran, it is output — do not commit it. `glossary.json` is
the only file in this list a human writes and a run merely *reads* — that is what makes it the one
exception.

## What changes when approval testing lands

The Java sibling's `.approved.nt` / `.received.nt` files are a genuinely different category — a
human-reviewed structural baseline is a decision, not output, and belongs in version control the
way a snapshot test's golden file does. This runtime does not have that mechanism yet; when it does,
this page gains the same two-category split Java documents (reviewed baseline: commit; everything
else: don't) rather than a rewrite from scratch.
