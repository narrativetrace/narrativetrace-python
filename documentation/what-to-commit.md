# What to commit

Two categories, not one. Almost everything NarrativeTrace writes is a **generated artifact
that describes one run** — nothing under your configured output directory is source, so none
of it belongs in version control. The one exception is the **approved trace**
(`.approved.nt`): a human reviewed it and accepted it as the
behavioral contract, the same way a snapshot test's golden file is a decision, not output —
see the [Structural Trace Format](structural-trace-format.md) page for the full grammar and
the approval-mode workflow.

| Artifact | Path pattern | Commit? | Why |
|---|---|---|---|
| Trace file (Markdown, default format) | `<OUTPUT_DIR>/traces/<Class>/<slug>.md` | No | Regenerated every run |
| Trace file (`text`/`mermaid`/`plantuml` format) | `<OUTPUT_DIR>/traces/<Class>/<slug>.{txt,mmd,puml}` | No | Regenerated every run |
| JSON scenario document (Markdown format only) | `<OUTPUT_DIR>/traces/<Class>/<slug>.json` | No | Same trace as canonical JSON — regenerated every run |
| Mermaid diagram companion (Markdown format only) | `<OUTPUT_DIR>/diagrams/<Class>/<slug>.mmd` | No | Regenerated every run |
| Canonical entry array | `<OUTPUT_DIR>/traces/<Class>/<slug>.canonical.json` | No | A machine artifact for conformance/porting, opt-in via `NARRATIVETRACE_CANONICAL` |
| Structural trace (`.nt`, the last-green baseline) | `<OUTPUT_DIR>/structural/<Class>/<slug>.nt` | No | Regenerated every green run — the *local* working copy, not the reviewed baseline below |
| **Approved trace** | `<APPROVED_DIR>/<Class>/<slug>.approved.nt` | **Yes**, once you opt into approval mode | The reviewed behavioral contract — a decision, not output |
| Received trace | `<APPROVED_DIR>/<Class>/<slug>.received.nt` | No | Written on a mismatch (or no baseline yet) for review; promote with `uv run poe approve` / `narrativetrace-approve`, never commit |
| Incomplete trace | `<APPROVED_DIR>/<Class>/<slug>.incomplete.nt` | No | Written instead of a received trace when the run itself was incomplete; the approve verb ignores it by name |
| `manifest.json` | `<OUTPUT_DIR>/manifest.json` | No | Regenerated every run — an index over the artifacts above, not a baseline itself; its top-level `run` object (`id`, `name` — the run's own three-word phrase) names *this session*, not a scenario, so it changes on every run even when nothing else does |
| Suite clarity report | `<OUTPUT_DIR>/clarity-report.md` | No | A generated report, not a decision |
| Suite clarity results | `<OUTPUT_DIR>/clarity-results.json` | No | Generated alongside the report |
| Standalone scanner output (`narrativetrace-clarity` CLI) | wherever `--output-dir` points | No | Same as above, generated on demand |
| `glossary.json` / `glossary.md` | repository root (or wherever you point `NARRATIVETRACE_GLOSSARY_DIR`) | **Yes**, if you use it | Human-owned vocabulary — the committed file is what clarity scoring reads back, and it is never regenerated by a test run. "One file, one review workflow" |
| `.claude/skills/**/SKILL.md`, the `AGENTS.md` `<!-- narrativetrace:skills:* -->` section | `.claude/skills/{add-narrative-tracing,narrativetrace-doctor}/SKILL.md`, `AGENTS.md` | **Yes** | Build output from `narrativetrace-skills-catalogue`'s typed catalogue (`python scripts/skills_render.py --fix`), not test-run output — committed the same way `glossary.json` is: regenerated, reviewed in diffs, and checked against drift (`python scripts/skills_render.py --check`, wired into `uv run poe check`) rather than hand-edited |
| `.agents/skills/**/SKILL.md` (and `.claude/skills/**` too, where detected), the `AGENTS.md` `<!-- narrativetrace:start … --> … <!-- narrativetrace:end -->` section, one `@AGENTS.md` line in `CLAUDE.md` | wherever `uv run narrativetrace init` writes in *your* project (not this repository's own dev copies above) | **Yes** | The same "reviewed, then committed" shape as `glossary.json`: `init --dry-run` shows the diff, a person reads it, `init` (no flag) writes it. Every installed page carries a `<!-- installed by narrativetrace init from <coordinate> — edit the catalogue, not this file -->` provenance line naming what it came from; `narrativetrace doctor`'s `config.skills-installed` check reads that stamp to tell you when a later release makes it stale, and `narrativetrace uninstall` removes exactly what `init` wrote (the marked section, the provenance-carrying pages, the one `CLAUDE.md` line) and nothing you added around it |
| `skills-lock.json` | project root, wherever `npx skills add` ran | **Yes**, if your team uses that tool | The registry's own lock file (source, content hash) — commit it the same way you would any other lock file your tooling depends on |
| `.claude-plugin/marketplace.json` | this repository's own root | **Yes** | This repository's own Claude Code plugin listing, rendered from the typed catalogue (`python scripts/skills_render.py --fix`) — committed build output, never hand-edited, gated against drift the same way the skill pages above are |

A personal plugin install (`/plugin marketplace add …`, `/plugin install …`) lands in your own
plugin cache, outside any project — it leaves nothing here to commit.

The default `<OUTPUT_DIR>` is `narrative-traces` and the default `<APPROVED_DIR>` is
`test-narratives` (both relative to wherever the suite ran, both configurable — see the
[Configuration Guide](guides/configuration.md)); ignore the output directory and the two
non-approved trace patterns under the approved directory:

```gitignore
narrative-traces/
test-narratives/**/*.received.nt
test-narratives/**/*.incomplete.nt
```

If you point `NARRATIVETRACE_OUTPUT_DIR`/`NARRATIVETRACE_APPROVED_DIR` somewhere else — a
`build/` directory, a CI artifacts folder — ignore those paths instead. `glossary.json` and
an approved trace are the two exceptions in this list: files a human writes (or reviews and
accepts) and a run merely *reads*, never overwrites — that is what makes them source.

## The rule in one sentence

If a file only exists because a test ran, it is output — do not commit it. If a file exists
because a human reviewed and accepted it, it is a baseline — commit it. `glossary.json` and
`.approved.nt` are the only two rows in this list a human writes or accepts; everything else
is regenerated.

## Approval mode, visually

```text
test passes
   |
   v
compare current structure to the approved trace
   |
   +-- same      --> pass, nothing written
   +-- different --> write a received trace and fail
                     |
                     v
                human reviews the diff
                     |
                     v
              uv run poe approve  (or narrativetrace-approve)
                     |
                     v
              .approved.nt updated, commit it
```

`.approved.nt` never contains parameter or return values — see
[Structural Trace Format](structural-trace-format.md) for the full grammar.
