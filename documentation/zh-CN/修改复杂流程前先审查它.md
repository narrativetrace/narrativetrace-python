# 修改复杂流程前先审查它

## 问题

> 在你修改结账流程之前,先告诉我它实际上做了什么。

读源码回答的是它*能*做什么。而一次运行回答的是,用这些输入它*实际*做了什么——按什么顺序、带着哪些值,以及流程在哪里离开了你即将编辑的代码。本页刻意从不展示实现:这正是读一次运行的意义所在。

## 最小配置

两份追踪产物除了[安装](安装指南.md)之外不需要任何东西。日志行需要一段普通的 `logging` 配置,与[给这个服务加日志](给这个服务加日志.md)里的完全一样。捕获级别是一项设置,而 `SUMMARY` 是本页在默认的 `DETAIL` 之外使用的那个:

```bash
NARRATIVETRACE_LEVEL=SUMMARY uv run pytest   # OFF | ERRORS | SUMMARY | NARRATIVE | DETAIL
```

参见[配置指南,追踪级别](配置指南.md)。

## 场景

对这个流程做一次有代表性的运行——借用一个现成的测试成本最低,而这就是那个测试:

```python
"""One successful checkout, the flow
documentation/recipes/review-a-complex-flow-before-changing-it.md is read before changing anything.

A fixture because two readers need the same run under different settings: ``recipe_artifacts.py``
runs it in its own pytest process once at DETAIL and once at SUMMARY. It passes either way --
nothing here fails by design. The log lines are the same flow through the project's own ``logging``
setup (``conftest.py``).
"""

from examples.recipes.checkout.order_service import OrderService
from examples.recipes.checkout.services import InventoryService, OrderRepository, PaymentService
from narrativetrace import ContextVarNarrativeContext, TraceId, export_to_logger, trace_object

# A fixed trace id, so the page's embedded artifacts name the same trace every run.
DEMO_TRACE_ID = TraceId("c4e1d0a7c4e1d0a7c4e1d0a7c4e1d0a7")


def test_a_customer_buys_two_keyboards(narrative_trace: ContextVarNarrativeContext) -> None:
    narrative_trace.adopt_trace_id(DEMO_TRACE_ID)

    stock = InventoryService("SKU-KB", 5)
    repository = OrderRepository()

    inventory = trace_object(stock, narrative_trace)
    payments = trace_object(PaymentService(), narrative_trace)
    orders = trace_object(repository, narrative_trace)
    checkout = trace_object(OrderService(inventory, payments, orders), narrative_trace)

    order_id = checkout.place_order("C-1234", "SKU-KB", 2, "4242424242424242")

    export_to_logger(narrative_trace.capture_trace())

    assert order_id == "ORD-C-1234-SKU-KB-2"
    assert stock.available_units("SKU-KB") == 3
    assert len(repository.saved()) == 1
```

## 如何阅读

**流程,来自 `DETAIL` 产物。** `#1` 是测试发起的那次调用,也是唯一的根:缩进在它下面的一切都发生在它内部,顺序就是打印的顺序。`#1.1` 在任何扣款之前预留两个单位;`#1.2` 扣款 7998——两个单位每个 3999,所以价格是由数量推导出来的,而不是传进来的;`#1.3` 保存的订单已经带着 `#1` 所返回的 id。读成一句话就是:这个结账流程先预留、再扣款、第三步保存,订单 id 在保存之前就已生成。先扣款再预留、或者先保存再扣款的改动,就是对*这个*流程的改动,而现在你不必相信某条注释就知道了这一点。

**每个级别是做什么的。** `DETAIL` 携带参数值,是你在处理这个流程时阅读的那个。在 `SUMMARY` 下,每个参数值都是空的——反引号里什么都没有——因为它们是在捕获时被抑制的,而不是在渲染时被隐藏的,而且只保留根调用和叶子调用;这个流程只有两层深,没有中间帧,所以出现的仍是同样的四次调用。更深的流程会丢掉它的中间部分。返回值在每个启用的级别都会保留:返回值是叙述的载荷。当你需要的是形状和结果、而值只是成本时——一次 CI 运行、一次长时间的浸泡测试——使用 `SUMMARY`;在生产环境里,在需要更多信息之前使用 `OFF`/`ERRORS`。

**哪份输出给人读,哪份给智能体读。** 日志行是给值班的人看的:它们与服务写的其他所有日志交错在一起,带着值,并以追踪的名字——`[solid wand romps]`——为键,所以一次结账可以从一份繁忙的文件里 grep 出来。`.nt` 是给智能体和评审者的:**按构造就不含值**——把它和上面的日志行比较,区别不在于值被替换了,而在于它们从未被写入。`(customer_id, sku, quantity, card_number)` 是参数*名*;`→ value` 表示返回了一个值,但不说是哪个(在 `reserve` 和 `save` 上它是 Python 的 `None`,仍然算数——没有 `void`)。这使它可以安全地提交、在评审中做 diff、交给模型:它不可能泄露客户 id,也不会因数据变化而变化——只有*调用*变了才会变。固定它就是[审查重构:行为变了吗](审查重构行为变了吗.md)。

## 没有捕获的内容

- **未被包装的对象内部的调用。** 包装了四个对象;它们背后的两个对象之间的调用,或者私有方法,永远不会出现。看起来很浅的流程可能其实很深。
- **所选的集成方式不会拦截的内容。** `trace_object` 只能看到*经过* wrapper 的调用:对象对自己发出的内部调用(`self._helper()`)它看不到,而该方法上的装饰器能看到。[选择集成方式](选择集成方式.md)按路径列出了取舍,而这正是其中会改变你在这里能读到什么的那一部分。
- **离开了线程的工作。** 交给 executor 却没有带上上下文的调用不会再往前追踪;追踪止于线程结束的地方。
- **被拒绝名单或值形态规则拦下的值**,这里是 `card_number` 和 `card`,在日志和 `DETAIL` 产物里都是 `[REDACTED]`,在 `.nt` 里则按构造就不存在。
- **一次运行,不是契约。** 换一个输入就会走另一条路径——缺货的 sku 根本到不了 `#1.2`。

**对应的技能:** `narrativetrace-verify`——它先写下意图,运行最小的真实路径,并在宣布任何事完成之前,对照这份意图阅读不含值的追踪。
