# 智能体技能

NarrativeTrace 提供**技能(skills)**:可由智能体加载的流程,执行经过测试的命令,并以 `verify`
步骤作为完成的判定标准,而不是一份智能体可能读也可能不读的文档。技能被设计得很"薄"——检查、
诊断或生成的逻辑都放在经过测试的库代码里;技能本身的工作只是知道何时该出手、调用那些经过测试
的代码,并在上下文中解读结果。

## 六个技能:配置、诊断、清晰度、报告、验证与调试

- **`add-narrative-tracing`** —— 把 NarrativeTrace 安装到一个项目中,并带它走到第一条追踪:
  用真实的工具链安装(`uv add narrativetrace`)、应用 doctor 打印出的每一条
  `config.<framework>-*` 修复来接入项目已在使用的框架(由已安装的 doctor 自带的框架表决定是哪些,
  所以技能页面不点名任何框架)、包装一个对象、渲染并运行第一条追踪,然后接入
  一个真正的日志系统(标准库 `logging` 桥接)。运行 `uv run narrativetrace doctor` 并把接力棒
  交出去——这是两个技能之间的接缝——最后以*预览*(从不应用)`narrativetrace init` 收尾,这样
  下一次会话无需任何人告知,就能发现这些技能已经装好了。
- **`narrativetrace-doctor`** —— 仅用于诊断,并且**只读**:它从不编辑、生成或删除文件。运行经过
  测试的 CLI,读取它的报告,并处理那些单纯的 CLI 输出本身无法覆盖的部分:在测试中证明脱敏确实
  生效、在做断言之前先阅读一条渲染出的追踪,以及审批追踪流程(标记为"尚未研究"——它自己的评估
  用例仍待完成)。
- **`add-narrativetrace-clarity`** —— 为项目加入命名清晰度关卡,并把它处理到通过:把
  `narrativetrace-clarity` 作为开发依赖安装(`uv add --dev`),扫描项目的包,检查报告**是新生成的、
  且至少给一个类打了分**——扫描在找不到任何类时会以 `0` 退出且不写任何文件,旧报告否则会冒充新
  报告——然后重命名报告指出的名字(用 `snake_case`,不管建议里的示例是什么写法),运行项目自己的
  测试,再用项目自己的阈值重新运行关卡,直到它以 `0` 退出。它绝不降低阈值,绝不加 `--warn-only`,
  也绝不为了读取词汇而去收集词汇表。这个运行时的关卡读取的是 Python 源码,因此没有经由测试运行器
  的路径;提交了词汇表的项目则通过 `narrativetrace_glossary.clarity_scan` 运行同一次扫描。
- **`narrativetrace-feedback`** —— 报告 NarrativeTrace 自身的缺陷:某项 doctor 检查有误或其修复无效、
  某个技能步骤无法照做、安装提示词中的措辞把人引向了错误的地方,或者在配置正确的项目上库的行为
  不正常。它背后经过测试的命令会根据项目起草报告(安装坐标、doctor 自己的 JSON 报告,以及至多一份
  结构化追踪),并且**拒绝写出带有你追踪中任何值的报告**——会指名拒绝它的那条规则,让你有具体的
  地方可改,而不是一条可以无视的警告。随后技能会展示完整的草稿,并只问一次是否公开提交。它不会
  把任何东西发送到任何地方,在没有你在自己的一轮对话中给出答复之前,也不会提交任何内容。
- **`narrativetrace-verify`** ——在智能体宣布改动完成之前,先读一读代码实际做了什么。它在测试已经
  变绿之后运行,第一步先判断这次改动值不值得追踪——纯函数或只改一个类的编辑不值得,技能会把这一点
  说出来然后停下。否则,它会在运行任何东西之前先写下意图(涉及哪些协作者、按什么顺序、走哪个分
  支、调用几次),开启追踪运行最小的真实路径(一个使用 `narrative_trace` fixture 的测试),对照这份
  意图阅读不含值的结构化追踪,只在看起来不对的那个 span 上打开值,修复后重新阅读,然后把这条流程
  固定为 `.approved.nt` 基线——审批模式关闭时先把它打开,以审批模式运行整个测试套件,展示完整的
  `.received.nt`,并且只有在你于独立一轮里说"是"之后才用 `narrativetrace-approve` 提升它。它的报告
  会引用 span id(`#2.1`),也就是每种呈现形式为同一个调用打印的位置,因此关于追踪的论断可以拿追踪
  本身来核对。
- **`narrativetrace-debug`** ——通过阅读代码对值做了什么来找出错误结果的原因,而不是单步调试。它从
  一个症状出发,而不是从一次改动出发:用最小的输入、开启追踪来复现症状,路径跨线程或 task 时先读时序
  图,然后在动任何代码之前,用 span id 指出第一个输入正确而结果错误的 span。它按 span 收窄,而不是按
  文件:只读该 id 之下的子树;当 span 内部的工作没有被追踪时,再用 `trace_object` 多包装一个协作者,
  而不是遮蔽任何东西(`not_traced_field`、`__nt_not_traced__` 和 `@not_traced` 会遮蔽一个值,它们并不
  限定追踪的范围)。它在那个 span 里修复缺陷,用同样的输入重新运行,并确认其他什么都没有变动——红色的
  运行不会写出 `.nt`,所以修复之前的形状就是复现用例 Markdown 中去掉值的调用行。它把复现用例保留为
  回归测试,通过与 `narrativetrace-verify` 相同的审批门把它的结构化追踪固定下来,并用 span id 报告
  根本原因。当追踪与代码不一致,或者缺陷属于 NarrativeTrace 本身时,它会交给
  `narrativetrace-feedback`,而不是绕过问题打补丁。

它们相互配合:一个全新的项目从 `add-narrative-tracing` 开始;一个已经安装了 NarrativeTrace、但
有些地方不对劲的项目,从 `narrativetrace-doctor` 开始。两条路径最终都会走到 doctor——诊断从此
由它负责。`add-narrativetrace-clarity` 负责命名报告及其关卡;它不安装追踪。`narrativetrace-feedback` 是当问题最终被证明出在我们这边、而不是项目那边时,路径的终点
——doctor 自己的收尾规则就指向它。`narrativetrace-verify` 是装好 NarrativeTrace 的会话在每次值得
追踪的改动之后要做的事——安装技能的最后一步会把下一个会话指向它,而 doctor 的
`config.approval-mode` 发现(没有任何东西去比较的基线)正是由它的固定步骤修复的。
`narrativetrace-debug` 是报告的症状的起点;它与验证技能共用阅读参考(哪种呈现形式回答哪个问题,以及
哪些形状意味着出了问题)和固定步骤,当缺陷属于我们时,它终于 `narrativetrace-feedback`。之后会有一个
技能负责生成(编写脱敏证明测试,这是今天 doctor 只能要求你添加、却不能
代劳的事)。

## `narrativetrace` 命令行工具

前两个技能会运行 `uv run narrativetrace doctor`——免费 CLI 的 `doctor` 命令,与 `init`/
`uninstall`(见下文[安装它们](#安装它们))、`feedback`(`narrativetrace-feedback` 背后的命令)以及
已有的 `narrativetrace-approve` 控制台脚本并列。
`doctor` 只读、零网络访问,`--json` 提供机器可读的输出,退出码 `0`(干净)、`1`(有发现项)或
`2`(无法运行)。十九项带有稳定、点分 id 的检查:解释器/pytest
版本是否符合声明、八个 `narrativetrace-*` 包是否统一在同一版本、`NARRATIVETRACE_OUTPUT` 的拼写
是否正确、pytest 插件的注册状态、NarrativeTrace 的智能体技能是否已安装且为最新、
`narrativetrace.toml` 中是否有无法识别的键、一个被导入却从未使用的脱敏标记、`*args` 方法的参数
是否坍缩成了单个 `args: [...]` 值、脱敏是否在测试中得到证明、过期的审批追踪差异、因审批模式关闭而无人比较的已批准基线,以及框架表每一行
各一项 `config.<framework>-*` 检查(框架表和每一行的接入代码见
[`llms-full.md`](../llms-full.md#framework-table--what-the-doctor-checks)):项目在用的某个框架,
其集成未添加,或已添加却从未接入,就会失败并给出要添加的代码行;尚未提供集成的框架只会被报告,
绝不靠猜。

`feedback draft | url | gh` 在同一份报告上提供三个通道。`draft` 把报告写到
`build/narrativetrace/feedback/` 下并完整打印出来;`url` 打印指向
`github.com/narrativetrace/narrativetrace-python` 的预填 issue 表单 URL,由你自己打开并用自己的
账号提交;`gh` 打印确切的 `gh issue create` 命令行,仅当 `gh` 已安装并已登录时才打印,而且从不
运行它。每个通道都会根据收到的参数重新起草,所以不会有任何东西在草稿被展示之后又改动的情况下
被提交。退出码 `0`(已起草)、`1`(该通道不可用,或文件系统拒绝写入文件)或 `2`(某条 `vf.*` 无值规则
拒绝了该报告且没有写入任何内容;或命令行无法解析)。提交是公开的:它会显示你的项目在使用
NarrativeTrace。

## 安装它们

`narrativetrace` 包(`uv add narrativetrace` 已经把它放进了你的 `PATH`)带有一个 `init` 命令,
可以帮你把六个技能都装好——零网络访问,而且在你说"好"之前什么都不会写入:

```bash
uv run narrativetrace init --dry-run
```

这就是 `--json` 信封;不加这个选项,同一条命令会把计划打印成统一 diff。读过之后,再去掉
`--dry-run` 重新执行一次,就会写入 `.agents/skills/`(一旦项目里有 `.claude/` 目录或
`CLAUDE.md`,或者加上 `--vendor claude`,也会写入 `.claude/skills/`),外加 `AGENTS.md` 里的一段
带标记的内容。`narrativetrace uninstall` 只会移除它写入的东西,不多不少;`narrativetrace doctor`
的 `config.skills-installed` 检查会在已安装内容过期时提醒你,所以之后保持更新只需要再跑一次
`init --dry-run`,不必再手工复制一遍文件。

仍是可行的退路:

- **Claude Code**:渲染好的 `SKILL.md` 文件位于本仓库的

  [`.claude/skills/narrativetrace-doctor/`](../../.claude/skills/narrativetrace-doctor/SKILL.md)、
  [`.claude/skills/narrativetrace-feedback/`](../../.claude/skills/narrativetrace-feedback/SKILL.md)、
  [`.claude/skills/add-narrativetrace-clarity/`](../../.claude/skills/add-narrativetrace-clarity/SKILL.md)、
  [`.claude/skills/narrativetrace-verify/`](../../.claude/skills/narrativetrace-verify/SKILL.md)
  和 [`.claude/skills/narrativetrace-debug/`](../../.claude/skills/narrativetrace-debug/SKILL.md)——
  目录名和 frontmatter 里的 `name:` 永远是目录中那个规范 id,绝不是缩短过的片段:仓库级别的
  `.claude/skills/` 目录本身就是一个扁平命名空间,不是 Claude 插件,所以像 `doctor` 这样缩短的
  名字会和其他任何厂商同名的技能冲突。把任意一个目录复制到你自己项目的 `.claude/skills/<name>/`
  下,Claude 会自动识别它,也可以直接按名字(`add-narrative-tracing` / `narrativetrace-doctor` /
  `narrativetrace-feedback` / `add-narrativetrace-clarity` / `narrativetrace-verify` /
  `narrativetrace-debug`)调用。
- **Codex CLI**:渲染好的 `SKILL.md` 文件位于本仓库的
  [`.agents/skills/add-narrative-tracing/`](../../.agents/skills/add-narrative-tracing/SKILL.md)、
  [`.agents/skills/narrativetrace-doctor/`](../../.agents/skills/narrativetrace-doctor/SKILL.md)、
  [`.agents/skills/narrativetrace-feedback/`](../../.agents/skills/narrativetrace-feedback/SKILL.md)、
  [`.agents/skills/add-narrativetrace-clarity/`](../../.agents/skills/add-narrativetrace-clarity/SKILL.md)、
  [`.agents/skills/narrativetrace-verify/`](../../.agents/skills/narrativetrace-verify/SKILL.md)
  和 [`.agents/skills/narrativetrace-debug/`](../../.agents/skills/narrativetrace-debug/SKILL.md)——
  Codex 自己当前的技能发现文档(已于 2026-09-14 核实)会从工作目录一路向上扫描到仓库根目录的
  `.agents/skills/<name>/SKILL.md`,所以它正是在这个路径下找到它们的,目录名和上面 Claude Code
  用的规范名称完全一致。frontmatter 只携带 `name` 和 `description`——Codex 文档里记载的那两个
  字段——下面的页面正文和 Claude Code 的逐字节完全相同。
- **任意智能体、任意平台**:每一个读取 `AGENTS.md` 的智能体都会看到本仓库自己的 `AGENTS.md` 在
  其 `<!-- narrativetrace:skills:start -->` 标记之间携带的常驻提示——每个技能的名称和描述都在
  其中,所以即便一个智能体从未想到要去查找它们,也依然知道它们的存在。
- **Gemini** 还没有自己的技能发现约定——已在路线图上,尚未构建。

## 来自注册表

一个项目可以在这里从未有人运行过 `init` 的情况下携带这些技能,处于以下三种状态之一:

1. **由 `init` 安装**—— 已提交,属于团队。这是 `config.skills-installed` 唯一会通过的状态:
   页面带有来源说明行,并且与本项目所解析的发行版本一致。
2. **来自注册表的个人安装**(一个 Claude Code 插件缓存)—— 只属于你。doctor 在设计上看不到它:
   它诊断的是项目,而个人安装既触达不到任何队友,也触达不到任何其他智能体。
3. **安装进项目的注册表版本**(`npx skills add`)—— 本仓库自己渲染出的页面,由注册表而不是
   `init` 落地,所以它们还不带来源说明行。

自己试一试这些技能,不触碰项目:

```text
/plugin marketplace add narrativetrace/narrativetrace-python
/plugin install narrativetrace-python@narrativetrace-python
```

然后运行 `uv run narrativetrace init --dry-run`,读一读 diff,再去掉该选项运行一次,让
`AGENTS.md` 指向它们。

从开放标准注册表安装进项目:

```text
npx skills add narrativetrace/narrativetrace-python
```

然后运行 `uv run narrativetrace init --dry-run`,读一读 diff,再去掉该选项运行一次,让
`AGENTS.md` 指向它们。

注册表留下的页面绝不会仅仅因为它在那里就被拒绝。`init` 会把它和自己原本会渲染出的内容逐字节
比较(只忽略换行符的差异)。一份和本发行版自己的页面完全相同的页面会被**采纳(adopted)**——
计划是这么说的,而不是"替换(replaced)",因为阅读它的人必须知道没有任何属于他们的东西被覆盖
了。这是计划本身的文字,原样引用,从不在这里重新敲一遍:

<!-- snippet: packages/narrativetrace-tooling/src/narrativetrace_tooling/init/plan_renderer.py region=adoptedNote -->
```python
ADOPTED = "adopted: identical to this carrier's page, so only the provenance line is added"
"""What the plan and the report say about a page that was already ours in everything but a line."""

```
<!-- /snippet -->

一份不同的页面——另一个发行版本的,或者被手工编辑过的——仍然保留 `--force` 存在的理由,即
普通的拒绝。`npx skills add` 还会把 `.claude/skills/<name>` 变成指向开放标准页面的一个符号
链接;`init` 永远不会透过这样的链接写入。一个链接,如果它指向的页面是本次安装会采纳或者已经
拥有的,就会被替换成一个真正的目录,装着正确的那个版本;其他任何链接都会被拒绝,因为
`--force` 只覆盖内容,从不覆盖链接。

而这是 doctor 自己的修复建议,同样原样引用,针对一个页面都在、却不带任何上述信息的项目:

<!-- snippet: packages/narrativetrace-tooling/src/narrativetrace_tooling/doctor/checks/skills_installed.py region=registryMessages -->
```python
_INIT_COMMAND = "uv run narrativetrace init --dry-run"

_READ_THE_DIFF = f"Run `{_INIT_COMMAND}`, read the diff, then run it without the flag."

_FROM_A_REGISTRY = (
    " Pages that are there without our line usually came from a registry (npx skills add, a plugin"
    " or workspace install). A page identical to this release's is adopted, and no --force is"
    " needed."
)
"""What a page with no provenance line most often IS: a registry install of this repository's own
rendered pages (design D5 state 3). Naming the case matters because the obvious reading of "not
ours" is "somebody else's work", which invites a ``--force`` nobody needs."""

```

## 它们是如何构建的

没有任何技能是手工编辑的。
`packages/narrativetrace-skills-catalogue/src/narrativetrace_skills/catalogue/add_narrative_tracing.py`、
`.../catalogue/narrativetrace_doctor.py`、`.../catalogue/narrativetrace_feedback.py` 和
`.../catalogue/add_narrativetrace_clarity.py` 是真相来源;
`python scripts/skills_render.py --fix` 会据此重新生成每个技能的 `.claude/skills/<name>/SKILL.md`、
它在 `.agents/skills/` 下的 Codex 版本,
以及本仓库自己 `AGENTS.md` 中的那一段,还有 `.claude-plugin/marketplace.json`——这份让本仓库
成为 Claude Code 插件市场的清单——而 `python
scripts/skills_render.py --check`(已接入 `uv run poe check`)只要其中任何一个与类型化的
源不同步,就会让构建失败。渲染出的页面展示的每一段代码,都通过本仓库其他文档已经在用的同一套
`<!-- snippet: -->` 标记约定,从真实、经过测试的源码中嵌入——绝不是手写的示例。一项 Tier A 检查
会把对私有规划笔记的引用挡在所有页面之外:说明性的句子可以保留,指名笔记的引用则不行。第二项检查
守护着唯一一处"缺失反而是特性"的 frontmatter:步骤可能让某些内容变为公开的技能——今天就是
`narrativetrace-feedback`——不得声明 `allowed-tools`,因为该字段会在加载该技能的那一轮对话中预先
批准它所列出的工具,而一个预先批准了自己报告命令的报告技能,会让运行环境在恰恰最需要询问的地方
不再询问。这类技能的 Claude Code 页面根本没有 `allowed-tools` 这一行,而不是一个空值。第三条 lint 出于同样
的理由,对会提升审批基线的技能——今天是 `narrativetrace-verify` 和 `narrativetrace-debug`——适用同一
条规则:提升通过 `uv run narrativetrace-approve` 运行,而它等待的那个"是"属于你。

## 评估它们

`packages/narrativetrace-skills-catalogue/evals/` 承载了 Tier B 套件(触发短语、每个技能一个"顺利路径"
用例、doctor 脱敏检查的一个偏差用例;清晰度技能的顺利路径从一个关卡会指出不清晰名字的 fixture 出发,
并以事后关卡通过为评分依据)——从不由 `poe check` 运行;由负责人手动执行,或从夜间任务
中执行,通过订阅制的 CLI,绝不使用按量计费的 API。关于 Codex/Gemini 的间歇性通道策略以及晋升
矩阵,参见[它自己的 README](../../packages/narrativetrace-skills-catalogue/evals/README.md)。
