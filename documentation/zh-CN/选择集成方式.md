# 选择集成方式

NarrativeTrace 只有一种捕获模型——一个通过管道发布的进入/退出事件——由数量不多的几种接入机制
触达。本页回答“我到底需要哪个包”这个问题:先给出一张速查表,再给出一张决策图,最后说明每条
路径各自的注意事项。

## 你想要... / 从这里开始...

| 你想要 | 从这里开始 |
|---|---|
| 在测试里获得追踪,接线最少 | `narrativetrace-pytest`(`narrative_trace` fixture) |
| 在纯 Python 中显式控制被包装的对象 | `trace_object(obj, context)`——核心包,不需要框架 |
| FastAPI/Starlette 的请求生命周期 | `narrativetrace-asgi` |
| 把追踪传播到下游的 HTTP 调用 | `narrativetrace-asgi` 的 `attach_traceparent`(httpx) |
| 在生产日志流中获得追踪 | `LoggingTraceConsumer` / `NarrativeContextFilter`(核心包) |
| structlog 流水线 | `narrativetrace-structlog` |
| OpenTelemetry span | `narrativetrace-otel` |
| 从一棵已捕获的树生成时序图 | `narrativetrace-diagrams` |
| 命名质量的 CI 门禁 | `narrativetrace-clarity` 控制台脚本 |
| Flask(WSGI)或 Django | 尚未发布——见下方*平台上限* |

这与[根目录 自述文件](../../自述文件.md)中的那张表是同一张;它也放在这里,作为下面决策图和
细节内容的锚点。

## 这个决策

只存在一个捕获原语——`trace_object(obj, context)`——它会直接、反射式地包装你传给它的那个具体
Python 对象实例。它不像基于动态代理的集成那样需要接口或基类,因此这个决策真正关心的是包装发生
在*哪里*,而不是一个对象*是否*够格:

```text
你希望追踪从哪里开始?
   |
   +-- 在我的测试套件内部 ----------------------> narrativetrace-pytest
   |                                            (narrative_trace fixture;无需手动包装)
   |
   +-- 围绕特定对象、简单脚本
   |   或应用代码 ------------------------------> 直接使用 trace_object(obj, context)(核心包)
   |
   +-- 贯穿一次 HTTP 请求的生命周期
   |     |
   |     +-- FastAPI / Starlette(ASGI)---------> narrativetrace-asgi
   |     +-- Flask / Django ---------------------> 尚未发布(见平台上限)
   |
   +-- 与已经跨线程或 asyncio task
       运行的代码协同 ---------------------------> 同上使用 trace_object,再加上一个
                                                  在边界处获取的上下文快照
                                                  (见下方跨线程工作)
```

这里没有零代码、字节码级别的接入机制(没有 import hook,也没有随附的 `sitecustomize.py`
自动插桩)——上面的每一条路径都是你的代码所做的显式调用,或者你自己注册的中间件,绝不会有
任何东西在加载时改写你的类。

## 所有路径共享的一件事

上面的所有机制都是从同一个 `TraceEvent` 流构建出同一棵 `TraceTree`——`trace_object` 的
`_TracedProxy`、pytest fixture,以及 ASGI 中间件,最终都会调用同一个上下文
(`ContextVarNarrativeContext.capture_trace()`);它们都没有各自定义“被捕获的调用”这个概念。
选择一种集成方式,问的是*调用是如何被包装的*,而不是一旦被记录之后会记录什么——按设计,每条
路径最终都会汇入同一个捕获入口,这是一个内部决策(PY-001、PY-004、PY-005),本页不需要重新
讨论。

## 每条路径各自的注意事项

- **`trace_object`** —— 包装你传给它的那个实例;一个指向*原始*未包装对象的引用会完全绕过捕获,
  因此应当在你的代码把对象交出去的那个点上包装(一个组合根、一个工厂、一个 fixture),而不是
  之后再包装。每一个公共方法(不以下划线开头)都会被自动追踪;除了装饰器之外,没有按方法
  逐一选择加入的名单。
- **`narrativetrace-pytest`** —— 作为 pytest 插件自动注册;`narrative_trace` fixture 为每个测试
  提供一个上下文,因此跨多个测试的追踪(一个会话级作用域的资源)需要你自己动手用
  `ContextVarNarrativeContext` 构建一个上下文。
- **ASGI(`narrativetrace-asgi`)** —— 只捕获 HTTP 作用域(`scope["type"] == "http"`);WebSocket
  和 lifespan 作用域会原样通过。`excluded_paths` 按请求路径的精确字符串匹配,而不是 glob 或
  前缀——排除 `/health` 只排除 `/health`,永远不会排除 `/health/live`。
- **跨线程 / 跨 task 的工作** —— `ContextVarNarrativeContext` 在设计上会隔离线程*和* asyncio
  task(各自拥有自己的视图)。提交给 `ThreadPoolExecutor` 或作为 `asyncio.Task` 启动的工作,
  只有通过 `ForkJoinGroup`/`FireAndForgetGroup`,或者在边界处获取的上下文快照,才会并入父级
  追踪——一个从未收到过这些的线程或 task 会保持隔离,它等价于 `captureTrace()` 的调用只会看到
  自己的那部分工作。一个已知的缺口:直接在一个被追踪的 `async def` 方法内部执行 fork,会通过
  同步调用栈解析父级,而这个栈在那里是空的,因此以这种方式启动的子任务会成为新的根节点,而不是
  嵌套在 `async` 调用方之下——请从一个同步方法或一个线程池中 fork,以保持嵌套结构。
- **`narrativetrace-otel`** —— 需要 `opentelemetry-api>=1.20`;它把一棵已经捕获好的 `TraceTree`
  桥接到 OTel span(批量导出器),或者实时监听——它不会替代 OpenTelemetry 自身的
  SDK/导出器配置。

## 平台上限

上面的每一条路径都假定运行在 CPython ≥ 3.12 上。Flask(WSGI)和 Django 中间件**已规划,尚未
发布**——与 `narrativetrace-asgi` 相同的请求边界契约是既定的目标形态,但今天还没有可安装的
软件包;状态见[功能指南](功能指南.md)。目前没有针对 PyPy 或 GraalPy 的兼容性测试。
