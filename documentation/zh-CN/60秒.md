# 60 秒看到一次追踪

不需要 `logger.info(...)` 语句,不需要测试框架,运行完也没有文件要打开——一个简单的脚本,运行
一次,追踪就直接打印在你的终端里。下面的一切都是针对发布在 PyPI 上的包真实运行的——输出是
粘贴过来的,不是想象出来的。

## 1. 新建项目,安装这个包

```bash
uv init myproject && cd myproject
uv add narrativetrace
```

## 2. 这段程序

`main.py` 采纳了一个固定的追踪 id——与 servlet 风格的边界处理入站追踪请求头所用的机制相同——
纯粹是为了让这个页面的输出每次都指向同一条追踪。你自己的代码永远不会这样做:真实的运行每次都
会生成一个随机的追踪 id,下面这个三词名字就是从它派生出来的,绝不是来自你选定的名字。

```python
# main.py
from narrativetrace import ContextVarNarrativeContext, IndentedTextRenderer, TraceId, trace_object


class OrderService:
    def place_order(self, customer_id, product_id, quantity):
        return f"ORD-{customer_id}-{product_id}-{quantity}"


# 一个固定的追踪 id,采纳它是为了让这个页面里嵌入的输出每次都指向同一条追踪。真实的运行每次
# 都会生成一个随机的(绝不是这个——这是本 DEMO 自己的常量,不是库的默认值),生成方式与
# servlet 风格的边界处理入站追踪请求头所用的 TraceId.adopt_trace_id 机制相同。
DEMO_TRACE_ID = TraceId("a1b2c3d4a1b2c3d4a1b2c3d4a1b2c3d4")

context = ContextVarNarrativeContext()
context.adopt_trace_id(DEMO_TRACE_ID)
service = trace_object(OrderService(), context)
service.place_order("cust-1", "prod-42", 3)

print(IndentedTextRenderer().render(context.capture_trace()))
```

## 3. 运行它

```bash
uv run main.py
```

```text
trace: loose hook parks (a1b2c3d)

OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3) → "ORD-cust-1-prod-42-3" — 0ms
```

`0ms` 也是真实的——这次调用在不到一毫秒内完成。换一台更慢的机器,或者一个更重的方法,数字会
更大;重点是它始终是被测量出来的,从不是编造的。

你没有写过一行日志语句。这一行来自方法名(`place_order`)、参数名(`customer_id`、
`product_id`、`quantity`)和真实的返回值——这些信息你的代码本来就有。

## 刚刚发生了什么

- **`ContextVarNarrativeContext()`** 是捕获上下文——你的代码运行时,进入/返回/异常事件就落在
  这里。它通过 `contextvars` 传播,所以会跟随 async task 和线程池里的工作,而不需要你手动传递
  它。
- **`trace_object(OrderService(), context)`** 包装了一个真实的实例。wrapper 上每一次公开方法
  调用都会被捕获;被包装的对象本身保持不变——没有基类,`place_order` 本身没有装饰器,也不需要
  注册。
- **`context.capture_trace()` 加上一个渲染器**把捕获到的事件变成文本。你刚才看到的是
  `IndentedTextRenderer`;`MarkdownRenderer` 会把同一次调用渲染成一条 Markdown 项目符号——这
  正是 `narrativetrace-pytest` 默认写到磁盘上的形式——而 `ProseRenderer` 读起来像一句话。同一条
  追踪,三种形态。

## 发送到你的日志系统

控制台那一行对脚本来说够用了;到了生产环境,你想要追踪出现在你已经在用的日志流里。
`export_to_logger` 一次调用就能把一条已经捕获好的追踪发送到你的日志系统——这正是 NarrativeTrace
自带的、桥接标准库 `logging` 的组件。下面注释标出的那些行就是相对第 1 步的改动;其余部分不变:

```python
# main.py
import logging  # 新增:标准库 logging——这一步把追踪发送到的目的地
import sys  # 新增:下面 handler 的 stdout 目标

from narrativetrace import (
    ContextVarNarrativeContext,
    IndentedTextRenderer,
    NarrativeContextFilter,  # 新增:把 traceName/runName 注入每条日志记录
    TraceId,
    export_to_logger,  # 新增:一次调用就把已捕获的追踪重放到你的日志系统
    trace_object,
)


class OrderService:
    def place_order(self, customer_id, product_id, quantity):
        return f"ORD-{customer_id}-{product_id}-{quantity}"


# 一个固定的追踪 id,采纳它是为了让这个页面里嵌入的输出每次都指向同一条追踪。真实的运行每次
# 都会生成一个随机的(绝不是这个——这是本 DEMO 自己的常量,不是库的默认值),生成方式与
# servlet 风格的边界处理入站追踪请求头所用的 TraceId.adopt_trace_id 机制相同。
DEMO_TRACE_ID = TraceId("a1b2c3d4a1b2c3d4a1b2c3d4a1b2c3d4")

# 新增:一个简单的标准库 logging 配置——和真实应用自己的 logging 配置形态一样
handler = logging.StreamHandler(sys.stdout)
handler.addFilter(NarrativeContextFilter())  # 新增:让下面能用到 traceName/runName
# 新增:DEBUG 级别让 export_to_logger 的记录能通过 handler;格式串读取过滤器写入的字段
logging.basicConfig(
    level=logging.DEBUG, format="[%(traceName)s] [%(runName)s] %(message)s", handlers=[handler]
)

context = ContextVarNarrativeContext()
context.adopt_trace_id(DEMO_TRACE_ID)
service = trace_object(OrderService(), context)
service.place_order("cust-1", "prod-42", 3)

trace = context.capture_trace()  # 新增:只捕获一次,print 和 export 共用同一条追踪
print(IndentedTextRenderer().render(trace))

export_to_logger(trace)  # 新增:把同一条已捕获的追踪发送到配置好的日志系统
```

```bash
uv run main.py
```

```text
trace: loose hook parks (a1b2c3d)

OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3) → "ORD-cust-1-prod-42-3" — 0ms
[loose hook parks] [] → OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3)
[loose hook parks] [] ← returned: "ORD-cust-1-prod-42-3"
```

(时间会有波动——`0ms` 就是你机器上测出来的数字,和上面一样;方括号里的短语始终不变——
`export_to_logger` 的重放沿用了被捕获追踪自身的 id,所以这里的 `traceName` 命名的正是上面固定的
那条追踪,而不是新生成的一条)。`traceName`
之所以有值,是因为有一条追踪处于活动状态;`runName` 在这里为空,是因为这个简单的脚本不属于任
何测试套件的运行——它只会在 `narrativetrace-pytest` 的 fixture 下才会被填充(参见[配置指南 §
运行也有名字](配置指南.md#运行也有名字))。同一条追踪现在也进入了你已经
有的日志目的地;控制台那一行没有变。用 `structlog` 的读者可以从 `narrativetrace-structlog` 拿到
完全一样的键集合——`NarrativeContextFilter`、MDC 键和请求级别的关联,详见完整的
[日志指南](日志与structlog指南.md)。
