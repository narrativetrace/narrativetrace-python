# 配置

## 配置从哪里来

每一项设置都通过同一条链路解析。第一个包含该键的来源胜出:

1. **环境变量** —— `NARRATIVETRACE_<KEY>`(键名全大写,所以 `output_dir` 读取
   `NARRATIVETRACE_OUTPUT_DIR`)
2. **`narrativetrace.toml`** —— 文档根级别的键
3. **`pyproject.toml`** —— `[tool.narrativetrace]` 下的键
4. **内置默认值**

配置文件的查找方式是从工作目录向上逐级查找。最近的、持有其中任一文件的目录胜出,查找到此为止。

**同一目录中存在两个配置来源是一个硬性错误。** 如果一个目录里同时有 `narrativetrace.toml` 和带
`[tool.narrativetrace]` 表的 `pyproject.toml`,解析会抛出 `DuplicateConfigurationError`,而不是
悄悄选择其中一个。一个格式错误的文件依然算作一个已声明的来源——一个损坏的配置应当大声地失败,
而不是靠抛硬币决定。

```toml
# narrativetrace.toml
level = "NARRATIVE"
output = true
output_dir = "narrative-traces"
format = "markdown"
```

```toml
# ...或者放在 pyproject.toml 里——同一目录中永远不要两者都放
[tool.narrativetrace]
level = "NARRATIVE"
output = true
```

```bash
# 环境变量始终优先,用于一次性覆盖
export NARRATIVETRACE_LEVEL=OFF
```

## 追踪级别

捕获由一个追踪级别控制,该级别在任何渲染发生*之前*就会被检查。级别是累加的——每一级都包含它
下面的一切。

| 级别 | 捕获内容 |
|---|---|
| `OFF` | 什么都不捕获(wrapper 直接短路;成本最低的路径) |
| `ERRORS` | 只捕获以错误结束或从未完成的路径 |
| `SUMMARY` | 入口点加上它们的叶子调用和错误调用,中间帧被折叠 |
| `NARRATIVE` | 完整的调用结构,附带已解析的 `@narrated` 文本 |
| `DETAIL` | 加上参数值和返回值(默认) |

参数值会在**捕获时**就被丢弃,低于 `DETAIL` 级别时无法在之后从更低级别的追踪中恢复。`ERRORS`
和 `SUMMARY` 还会在捕获之后对树做剪枝。

可以在代码中、配置文件中,或通过环境变量设置它:

```python
from narrativetrace import ContextVarNarrativeContext, NarrativeTraceConfig, TracingLevel

context = ContextVarNarrativeContext(NarrativeTraceConfig(level=TracingLevel.NARRATIVE))
```

`NarrativeTraceConfig.resolve()` 会针对 `level` 键运行上面的那条链路。未知或空值会降级为默认值,
而不是抛出异常——错误配置绝不能把捕获功能一起拖垮。级别名称不区分大小写。

## 输出设置(pytest 插件)

| 键 | 环境变量 | 含义 | 默认值 |
|---|---|---|---|
| `output` | `NARRATIVETRACE_OUTPUT` | 真值 → 写出逐测试的产物 | 开启 *(since 0.1.2, unreleased)* |
| `output_dir` | `NARRATIVETRACE_OUTPUT_DIR` | 产物目录 | `narrative-traces` |
| `format` | `NARRATIVETRACE_FORMAT` | `markdown` / `text` / `mermaid` / `plantuml` | `markdown` |
| `level` | `NARRATIVETRACE_LEVEL` | fixture 上下文的捕获级别 | `DETAIL` |
| `glossary_dir` | `NARRATIVETRACE_GLOSSARY_DIR` | 存放已提交的 `glossary.json` 的目录,作为清晰度评分所用的词汇表读取(见 [清晰度指南](清晰度指南.md)) | 工作目录 |
| `canonical` | `NARRATIVETRACE_CANONICAL` | 同时写出逐测试的 `<test>.canonical.json` 条目数组 | `false` |

`output` 默认开启 *(since 0.1.2, unreleased)* —— PyPI 上发布的 `0.1.1` 仍然默认关闭:`narrative_trace`
fixture 会在不做任何配置的情况下,把每个非空测试的产物写到
`narrative-traces/` 下。可通过 `NARRATIVETRACE_OUTPUT=false`(`0`/`no`/`off` 同样有效,且不区分
大小写)或在配置文件中设置 `output = false` 来关闭。将该目录加入 `.gitignore` 的做法见
[应提交的内容](应提交的内容.md)。

无论词汇表文件是否存在,`glossary_dir` 都会被读取:读取不会改变磁盘上的任何内容,所以不需要
显式开启,而没有该文件的仓库仅使用内置词典进行评分。

格式名称的比较不区分大小写。只有 `markdown` 会写出成对的附属文件(一个同名的 `.json` 规范导出
文件和一个 Mermaid 的 `.mmd`);`text`、`mermaid` 和 `plantuml` 会用各自这一份产物取代 Markdown
追踪文件。

`canonical` 与 `format` 相互独立:一次选择了 `text` 或 `mermaid` 作为人类可读产物的运行,依然
要为一致性校验器提供其条目。该文件是一个扁平的 JSON 数组,包含 schema `1.2` 的规范条目,每次
被追踪的调用对应一个 `method_enter` 和一个 `method_exit`,每一条都能通过 `entry.schema.json`
的校验。默认关闭,因为它是一个面向机器的产物——服务于其他实现、一致性夹具和翻译——而不是用来在
失败后阅读的东西。

## 服务身份

在每个 span 上盖印服务元数据,用于关联:

```python
from narrativetrace import ServiceIdentity

context = ContextVarNarrativeContext(service_identity=ServiceIdentity("orders", "1.4.0", "prod"))
```
