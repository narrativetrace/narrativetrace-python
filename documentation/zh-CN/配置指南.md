# 配置

## 配置从哪里来

每一项设置都通过同一条链路解析。第一个包含该键的来源胜出:

1. **环境变量** —— `NARRATIVETRACE_<KEY>`(键名全大写,所以 `output_dir` 读取
   `NARRATIVETRACE_OUTPUT_DIR`)
2. **`narrativetrace.toml`** —— 文档根级别的键
3. **`pyproject.toml`** —— `[tool.narrativetrace]` 下的键
4. **内置默认值**

配置文件的查找方式是从工作目录向上逐级查找。最近的、持有其中任一文件的目录胜出,查找到此为止。

**同一目录中存在两个配置来源是一个硬性错误。** 如果一个目录里同时有 `narrativetrace.toml` 和带
`[tool.narrativetrace]` 表的 `pyproject.toml`,解析会抛出 `DuplicateConfigurationError`,而不是
悄悄选择其中一个。一个格式错误的文件依然算作一个已声明的来源——一个损坏的配置应当大声地失败,
而不是靠抛硬币决定。

```toml
# narrativetrace.toml
level = "NARRATIVE"
output = true
output_dir = "narrative-traces"
format = "markdown"
```

```toml
# ...或者放在 pyproject.toml 里——同一目录中永远不要两者都放
[tool.narrativetrace]
level = "NARRATIVE"
output = true
```

```bash
# 环境变量始终优先,用于一次性覆盖
export NARRATIVETRACE_LEVEL=OFF
```

## 追踪级别

捕获由一个追踪级别控制,该级别在任何渲染发生*之前*就会被检查。级别是累加的——每一级都包含它
下面的一切。

| 级别 | 捕获内容 |
|---|---|
| `OFF` | 什么都不捕获(wrapper 直接短路;成本最低的路径) |
| `ERRORS` | 只捕获以错误结束或从未完成的路径 |
| `SUMMARY` | 入口点加上它们的叶子调用和错误调用,中间帧被折叠 |
| `NARRATIVE` | 完整的调用结构,附带已解析的 `@narrated` 文本 |
| `DETAIL` | 加上参数值和返回值(默认) |

参数值会在**捕获时**就被丢弃,低于 `DETAIL` 级别时无法在之后从更低级别的追踪中恢复。`ERRORS`
和 `SUMMARY` 还会在捕获之后对树做剪枝。

可以在代码中、配置文件中,或通过环境变量设置它:

```python
from narrativetrace import ContextVarNarrativeContext, NarrativeTraceConfig, TracingLevel

context = ContextVarNarrativeContext(NarrativeTraceConfig(level=TracingLevel.NARRATIVE))
```

`NarrativeTraceConfig.resolve()` 会针对 `level` 键运行上面的那条链路。未知或空值会降级为默认值,
而不是抛出异常——错误配置绝不能把捕获功能一起拖垮。级别名称不区分大小写。

## 排除库与生成的代码

`trace_object` 恰好包装你交给它的对象——这就是包含列表,没有任何 import hook 会扩大它。随后由两个排除列表决定什么永远不被追踪,各有各的负责方:

1. **内置,不可配置。** 在 Python 中结构上永远不是业务边界的东西。没有任何设置能重新启用它,也从不报告。
2. **可配置,带内置默认值。** 库和框架的内部实现,按模块前缀命名。提供 `exclude` 键会*替换*默认值(以键是否存在为准,与这里的每个键一样);要扩展默认值,请重复写出它的条目。

```python
from narrativetrace import trace_object

service = trace_object(OrderService(), context)                     # 已包装:这就是包含
service = trace_object(OrderService(), context, exclude="acme.fakes")  # ...除非它的模块被排除
```

```toml
# narrativetrace.toml(或 [tool.narrativetrace]);NARRATIVETRACE_EXCLUDE 设置同一个键
exclude = "acme.fakes;unittest;pytest"     # 以 ';' 分隔,或使用 TOML 数组
```

被排除的目标会原样从 `trace_object` 返回(不包装),其调用不被追踪;排除优先于包装。前缀与定义目标类型的模块比较,以 `.` 为边界:`acme.fakes` 覆盖 `acme.fakes.deep`,但不覆盖 `acme.fakesx`。每个匹配的前缀会在 stderr 输出一行说明,绝不按目标重复。`narrativetrace doctor`(`config.exclude`)会打印生效的列表,并在值无法解析时失败;修正之前使用默认值。

**列表 1 —— 内置**

| 永不追踪 | 结构性特征 |
|---|---|
| `builtins.*` | 目标的类型由解释器自身定义(`list`、`dict`、`str`) |
| `functools.partial` | `functools.partial` / `partialmethod` 对象,无论作为目标还是成员 |
| `types.BuiltinFunctionType` | 由 C 运行时提供的成员:内置函数、已绑定的内置方法、method wrapper、slot wrapper、method descriptor |
| `<lambda>` | `__name__` 不是标识符的成员(`<lambda>`、`<genexpr>`) |
| `_name` | `_私有` 或 `__dunder__` 成员:运行时为自身调用的机制 |

`functools.lru_cache` 包装器和用 `functools.wraps` 装饰的函数不在其中:带缓存的业务方法仍然是值得看的边界。

**列表 2 —— 内置默认值**

| 模块前缀 | 排除原因 |
|---|---|
| `unittest` | 标准库的测试运行器,以及作为 `unittest.mock` 的模拟库:生成的 `Mock` 子类会记录它收到的每次调用 |
| `mock` | `unittest.mock` 在 PyPI 上的向后移植版,同样生成模拟类 |
| `pytest_mock` | pytest-mock 围绕 `unittest.mock` 的辅助工具 |
| `pytest` | 测试运行器自身的辅助工具 |
| `_pytest` | 测试运行器的私有实现,插件和 fixture 会调用它 |
| `pluggy` | pytest 的钩子调用机制 |
| `hypothesis` | 属性测试引擎自身的辅助工具和策略 |
| `coverage` | coverage.py 的跟踪器和报告器 |
| `narrativetrace` | 本库自身的类型:追踪它们就是追踪追踪器 |
| `ddtrace` | 另一个 APM 代理的运行时:共存时避免递归插桩 |
| `opentelemetry` | 最可能共存的另一个 APM 运行时,原因相同 |

## 两个旋钮,两条路径

**我把追踪级别设为 `DETAIL`,但日志里什么都没出现。或者:我把 logger 设为 `WARNING`,追踪结果却
依然出现在我的 pytest 产物里。到底哪个设置说了算?**

两个都算,因为它们回答的是不同的问题。NarrativeTrace 有两个旋钮,而把一条已捕获的追踪送进你的
logger,是与捕获它本身完全分开的一步。

**旋钮一,追踪级别,决定什么会被捕获。** `OFF`、`ERRORS`、`SUMMARY`、`NARRATIVE`、`DETAIL`——
累加式,每一级都包含它下面的一切(见上表)。这是 NarrativeTrace 自己的设置,它在两个不同的点上
起作用,而不是只有一个:处于 `OFF` 时,`context.is_active()` 为 `False`,`trace_object` 的包装
器会完全跳过拦截——被包装的调用运行时完全不触碰捕获机制,对任何消费者来说都不会产生任何事件。
从 `ERRORS` 开始,每次调用*都会*被拦截并记录下来——`ERRORS` 和 `SUMMARY` 并不会跳过拦截,它们
是在捕获*之后*对生成的树做剪枝(丢弃没有错误的路径、折叠中间帧);只有低于 `DETAIL` 时,参数值
才会在捕获时就被省略,之后无论 logger 怎么设置都无法恢复。没有其他设置能找回 `OFF` 跳过的东西,
或者只有 `DETAIL` 才会捕获的东西。

**旋钮二,你的 logger 级别,决定什么会被打印出来——前提是一条追踪确实到达了你的 logger。**
默认情况下,什么都不会到达:除非你自己把一条追踪发送过去,否则 NarrativeTrace 不会向
`logging.getLogger("narrativetrace")`(`LoggingTraceConsumer` 默认使用的 logger 名)写入任何
内容。当你这么做时,每种行都有各自的默认级别:进入和返回都在 `DEBUG`(Python 标准库 `logging`
没有对应 Java `TRACE` 的级别),异常在 `WARNING`,格式为 `!! {type}: {message}
[{error_context}]`。你的 logger 的阈值随后会照常发挥作用——调高它会让某些行不再打印,但它既
不会让捕获多一点,也不会让捕获少一点。

**现在说说两条路径,这正是困惑的来源。** 被捕获的追踪——`capture_trace()` 返回的一切,以及
依赖它的一切:pytest 插件逐测试的产物、`.nt` 批准基线、清晰度报告、`TraceSpanExporter` 的批量
OpenTelemetry 导出、渲染出的叙述文本——在每个方法进入和退出的那一刻,就直接写入了上下文自身的
事件存储。这次写入完全不会查询你的 logger,无论哪个方向都不会:把 `narrativetrace` 这个 logger
调到 `CRITICAL` 不会让它变少,完全不接 logger 也一样不会。

把一条已捕获的追踪送进你的 logger,是一个独立、显式的步骤,通过 `LoggingTraceConsumer` 完成,
有两种方式:

- **捕获后回放** —— `export_to_logger(trace)` 一次调用就把一棵已经完成的 `TraceTree` 送入一个
  私有的 `LoggingTraceConsumer`。这是[60 秒教程](60秒.md#发送到你的日志系统)以及本仓库每一份
  指南都在用的方式。
- **实时地,随事件发生** —— 把一个 `LoggingTraceConsumer` 挂到你自己组装的 `DualPathPipeline`
  的同步监听器位置,通常还会搭配一个 `BufferedEventConsumer` 作为它的尽力而为路径(一个有界
  环形缓冲区,默认 65,536 条事件,压力下会丢弃负载,每一次丢失都会被计数——见
  [并发](../../README.md#concurrency)),用来给任何其他实时消费者提供数据,包括
  `OtelTraceEventListener`,它们由同一条事件流喂给。

无论哪种方式,日志行和追踪产物都是对同一批被捕获事件的两个独立读取者。调高 `narrativetrace`
这个 logger 的级别只会让日志行安静下来;它碰不到 `capture_trace()` 的输出,因为那份输出压根
就没经过 logger。

**每个旋钮住在哪里。**

| 旋钮 | 住在哪里 |
|---|---|
| 追踪级别 | 环境变量 `NARRATIVETRACE_LEVEL`;`narrativetrace.toml` 或 `pyproject.toml` 中 `[tool.narrativetrace]` 下的 `level`;代码中的 `NarrativeTraceConfig(level=TracingLevel.X)` |
| logger 阈值 | 对 `logging.getLogger("narrativetrace")` 的普通 `logging` 配置——这是 `LoggingTraceConsumer` 默认使用的名字 |
| 每种行的级别 | `LoggingTraceConsumer(levels={EventType.ENTRY: ..., EventType.RETURN: ..., EventType.EXCEPTION: ...})`,或者把同样的 `levels=` 参数传给 `export_to_logger(trace, levels=...)` |

**经验法则。** 想减少日志量,就调高 `narrativetrace` 这个 logger 的阈值;被捕获的追踪不受影响。
想减小追踪的体积,就调低追踪级别——`ERRORS`/`SUMMARY` 会在捕获之后对它剪枝。想降低开销,就把
追踪级别调到 `OFF`:这是唯一会跳过拦截本身的一步;`ERRORS`、`SUMMARY` 和 `NARRATIVE` 依然会像
`DETAIL` 一样拦截并记录每一次调用,只是渲染的值更少、之后剪枝更多。logger 阈值在任何级别下都
不会改变捕获成本。想在生产环境里保留追踪功能但不进日志,就把追踪级别留在 `SUMMARY` 或更高,
然后要么完全不把追踪发给 logger,要么发给它并把 `narrativetrace` 这个 logger 设为 `WARNING`:
无论哪种做法,`capture_trace()` 及依赖它的一切都会保持完整。

## 输出设置(pytest 插件)

| 键 | 环境变量 | 含义 | 默认值 |
|---|---|---|---|
| `output` | `NARRATIVETRACE_OUTPUT` | 真值 → 写出逐测试的产物 | 开启 |
| `output_dir` | `NARRATIVETRACE_OUTPUT_DIR` | 产物目录 | `narrative-traces` |
| `format` | `NARRATIVETRACE_FORMAT` | `markdown` / `text` / `mermaid` / `plantuml` | `markdown` |
| `level` | `NARRATIVETRACE_LEVEL` | fixture 上下文的捕获级别 | `DETAIL` |
| `glossary_dir` | `NARRATIVETRACE_GLOSSARY_DIR` | 存放已提交的 `glossary.json` 的目录,作为清晰度评分所用的词汇表读取(见 [清晰度指南](清晰度指南.md)) | 工作目录 |
| `canonical` | `NARRATIVETRACE_CANONICAL` | 同时写出逐测试的 `<test>.canonical.json` 条目数组 | `false` |
| `approval` | `NARRATIVETRACE_APPROVAL` | 真值 → 针对已提交的已批准追踪校验结构 | `false` |
| `approved_dir` | `NARRATIVETRACE_APPROVED_DIR` | 存放已提交的 `*.approved.nt` 追踪的目录 | `test-narratives` |

`output` 默认开启:`narrative_trace`
fixture 会在不做任何配置的情况下,把每个非空测试的产物写到
`narrative-traces/` 下。可通过 `NARRATIVETRACE_OUTPUT=false`(`0`/`no`/`off` 同样有效,且不区分
大小写)或在配置文件中设置 `output = false` 来关闭。将该目录加入 `.gitignore` 的做法见
[应提交的内容](应提交的内容.md)。

无论词汇表文件是否存在,`glossary_dir` 都会被读取:读取不会改变磁盘上的任何内容,所以不需要
显式开启,而没有该文件的仓库仅使用内置词典进行评分。

格式名称的比较不区分大小写。只有 `markdown` 会写出成对的附属文件(一个同名的 `.json` 规范导出
文件和一个 Mermaid 的 `.mmd`);`text`、`mermaid` 和 `plantuml` 会用各自这一份产物取代 Markdown
追踪文件。

`canonical` 与 `format` 相互独立:一次选择了 `text` 或 `mermaid` 作为人类可读产物的运行,依然
要为一致性校验器提供其条目。该文件是一个扁平的 JSON 数组,包含 schema `1.2` 的规范条目,每次
被追踪的调用对应一个 `method_enter` 和一个 `method_exit`,每一条都能通过 `entry.schema.json`
的校验。默认关闭,因为它是一个面向机器的产物——服务于其他实现、一致性夹具和翻译——而不是用来在
失败后阅读的东西。

## 结构化产物与审批模式

Markdown 路径还会在叙事文件旁边写出一份无值的结构化 `.nt` 产物——语法见
[结构化追踪格式](结构化追踪格式.md)。磁盘上的这个文件是**最近一次绿色基线**:一次绿色运行会
推进它,一次非绿色运行会与它比较但绝不会覆盖它,所以每一份差异读起来都是"自从这个场景上一次
通过以来发生了什么变化"。"绿色"是整体判定,不只是断言——一个测试通过了,但其结构被审批模式
*拒绝*的运行,最终判定为非绿色,其结构不会被写入。因此拒绝一次变更会让基线保持原样,回退这次
变更也不会报告任何差异。

`approval` 打开审批模式:在一个**通过**的测试之后,该场景的无值结构会与已提交的基线
`<approved_dir>/<TestClassName>/<slug>.approved.nt` 进行核对。缺失的基线或结构差异会让测试
失败,并给出一份可读的差异,同时在基线旁边把当前结构写为 `*.received.nt`。审阅它,然后用
`uv run poe approve`(或读取同一个 `approved_dir` 键的 `narrativetrace-approve` 控制台脚本)
提升它。失败的测试永远不会被核对——审批只评判本来会通过的测试。

每次运行还会写出 `<output_dir>/manifest.json`:一个顶层的 `run` 对象(`id`、`name`——运行自己
的三词短语,参见下文的[运行也有名字](#运行也有名字)),后面跟着
每个被追踪的场景一行,记录它的测试、方法运行超过一次时的调用编号,以及它拥有的每一个产物:

```json
{
  "schema": "narrativetrace/scenario-manifest/1",
  "run": {
    "id": "a1b2c3d4a1b2c3d4a1b2c3d4a1b2c3d4",
    "name": "bold elk soars"
  },
  "scenarios": [
    {
      "scenario": "find TENT",
      "testClass": "CatalogTest",
      "testMethod": "test_finds_it",
      "invocation": 2,
      "artifacts": {
        "trace": "traces/CatalogTest/test_finds_it-002-tent.md",
        "structural": "structural/CatalogTest/test_finds_it-002-tent.nt"
      }
    }
  ]
}
```

套件页脚还会额外打印一行,汇总每个场景的结构化状态:

```text
NarrativeTrace — Suite complete
  run: bold elk soars
  2 scenarios recorded
  Clarity: 100% high | 0% moderate | 0% low
  Reports: narrative-traces
  Since last green: 1 scenario unchanged · 1 changed: "Customer places order" (+1 call InventoryService.release)
```

当结构确实发生变化时,一次失败测试的控制台报告会打印相对于最近一次绿色产物的结构化差异,
而不是完整的追踪。

### 运行也有名字

 每次 pytest 会话都会生成一个运行 id——由插件自己的
`pytest_sessionstart` 钩子生成——一个 W3C 形状的 id,绝不是共享常量——它的三词短语(与追踪 id
的名字来自同一个命名器)就是**运行名称**。它出现在:

- 控制台套件的页脚里(`run: bold elk soars`,如上);
- `manifest.json` 顶层的 `run` 对象里(`id` 和 `name`,如上);
- 每份 Markdown 追踪文档的 YAML frontmatter 里(`run: bold elk soars`,与 `scenario:` 并列);
- 标准库日志桥接中类似 MDC 的上下文里的 `runName`,代表整个会话(参见[日志指南](日志与structlog指南.md)),
  这样一次 grep 就能找到某次运行的全部日志行。

运行名称及其 id 受到与追踪自身名字相同的不变式保护:它们**绝不**会进入结构化 `.nt` 文本、一份
已审批或已接收的追踪、某个产物的文件名,或清单里按场景划分的键——用两个不同的运行名称把同一
套件运行两次,产出的 `.nt` 文件与 delta 输出每次都逐字节相同。追踪自身的名字(控制台/缩进渲染
器里的 `trace: bold elk soars (a1b2c3d)`、散文里的 `The trace bold elk soars:`、Markdown 标题
行里的那个短语)是*另一回事*——每条追踪一个,而不是每次运行一个——同样不会出现在 `.nt` 文本里。

## 服务身份

在每个 span 上盖印服务元数据,用于关联:

```python
from narrativetrace import ServiceIdentity

context = ContextVarNarrativeContext(service_identity=ServiceIdentity("orders", "1.4.0", "prod"))
```

只有名称是必需的;`ServiceIdentity("orders")` 会让版本和环境保持未设置。完全省略时,上下文会从环境中
读取同样这三个值:

| 环境变量 | 对应 |
|---|---|
| `NARRATIVETRACE_SERVICE_NAME` | 服务名称 |
| `NARRATIVETRACE_SERVICE_VERSION` | 服务版本 |
| `NARRATIVETRACE_ENVIRONMENT` | 部署环境 |

名称为空白即表示没有身份——没有名称的版本或环境会被忽略——传给上下文的身份优先于环境变量。它们只是环境变量:
`narrativetrace.toml` 中没有对应的键。两者都没有时,每条追踪在平台和 OpenTelemetry 中都显示为
`unknown_service:python`。当非测试代码构造了 `ContextVarNarrativeContext` 而没有任何东西给服务命名时,
`narrativetrace doctor`(`config.service-identity`)会报告失败。

## 扩充脱敏默认值

有两个旋钮,作用不同。

```bash
# 在内置词表之上追加(以逗号分隔的字段名子串)
export NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS=betalingskort,kontonummer
```

```python
# 完全替换内置词表
ValueRenderer(redaction_policy=RedactionPolicy.of_patterns({"ssn", "internal_ref"}))
```

环境变量面向*部署*服务的人——无需重新构建,并且在构造策略时只从环境变量读取,不读取 `narrativetrace.toml` 或
`pyproject.toml`。`of_patterns` 面向*编写*应用的人。两者可以叠加:追加项仍然适用于用 `of_patterns` 构造的策略,因为替换词表只是应用对
自身哪些字段敏感的判断,而不是撤销部署方扩充的许可。`RedactionPolicy.DISABLED` 会忽略它们。完整约定:
[隐私与脱敏](隐私与脱敏.md)。

> **追加项是子串模式**,匹配方式与内置的子串词表完全相同。过短的追加项会带来按 token 匹配的词所避免的陷阱:追加 `id` 会脱敏追踪中的每一个标识符。
