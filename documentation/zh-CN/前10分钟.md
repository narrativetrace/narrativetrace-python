# 60 秒看到一次追踪

不需要 `logger.info(...)` 语句,不需要测试框架,运行完也没有文件要打开——一个简单的脚本,运行
一次,追踪就直接打印在你的终端里。下面的一切都是针对发布在 PyPI 上的包(`narrativetrace`
0.1.1)真实运行的——输出是粘贴过来的,不是想象出来的。

## 1. 新建项目,安装这个包

```bash
uv init myproject && cd myproject
uv add narrativetrace
```

## 2. 这段程序

```python
# main.py
from narrativetrace import ContextVarNarrativeContext, IndentedTextRenderer, trace_object


class OrderService:
    def place_order(self, customer_id, product_id, quantity):
        return f"ORD-{customer_id}-{product_id}-{quantity}"


context = ContextVarNarrativeContext()
service = trace_object(OrderService(), context)
service.place_order("cust-1", "prod-42", 3)

print(IndentedTextRenderer().render(context.capture_trace()))
```

## 3. 运行它

```bash
uv run main.py
```

```text
OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3) → "ORD-cust-1-prod-42-3" — 0ms
```

`0ms` 也是真实的——这次调用在不到一毫秒内完成。换一台更慢的机器,或者一个更重的方法,数字会
更大;重点是它始终是被测量出来的,从不是编造的。

你没有写过一行日志语句。这一行来自方法名(`place_order`)、参数名(`customer_id`、
`product_id`、`quantity`)和真实的返回值——这些信息你的代码本来就有。

## 刚刚发生了什么

- **`ContextVarNarrativeContext()`** 是捕获上下文——你的代码运行时,进入/返回/异常事件就落在
  这里。它通过 `contextvars` 传播,所以会跟随 async task 和线程池里的工作,而不需要你手动传递
  它。
- **`trace_object(OrderService(), context)`** 包装了一个真实的实例。wrapper 上每一次公开方法
  调用都会被捕获;被包装的对象本身保持不变——没有基类,`place_order` 本身没有装饰器,也不需要
  注册。
- **`context.capture_trace()` 加上一个渲染器**把捕获到的事件变成文本。你刚才看到的是
  `IndentedTextRenderer`;`MarkdownRenderer` 会把同一次调用渲染成一条 Markdown 项目符号——这
  正是 `narrativetrace-pytest` 默认写到磁盘上的形式——而 `ProseRenderer` 读起来像一句话。同一条
  追踪,三种形态。

## 发送到你的日志系统

控制台那一行对脚本来说够用了;到了生产环境,你想要追踪出现在你已经在用的日志流里。通过
`LoggingTraceConsumer`——NarrativeTrace 自带的、桥接标准库 `logging` 的组件——把它转发出去,
做法是给上下文一个你之后能读回来的 `EventStore`:

```diff
 # main.py
-from narrativetrace import ContextVarNarrativeContext, IndentedTextRenderer, trace_object
+import logging
+import sys
+
+from narrativetrace import ContextVarNarrativeContext, IndentedTextRenderer, LoggingTraceConsumer, trace_object
+from narrativetrace.pipeline.event_store import EventStore
 

 class OrderService:
     def place_order(self, customer_id, product_id, quantity):
         return f"ORD-{customer_id}-{product_id}-{quantity}"


-context = ContextVarNarrativeContext()
+logging.basicConfig(level=logging.DEBUG, format="%(message)s", stream=sys.stdout)
+
+store = EventStore()
+context = ContextVarNarrativeContext(store=store)
 service = trace_object(OrderService(), context)
 service.place_order("cust-1", "prod-42", 3)

 print(IndentedTextRenderer().render(context.capture_trace()))
+
+consumer = LoggingTraceConsumer()
+for event in store.events():
+    consumer.accept(event)
```

```bash
uv run main.py
```

```text
OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3) → "ORD-cust-1-prod-42-3" — 0ms
→ OrderService.place_order(customer_id: "cust-1", product_id: "prod-42", quantity: 3)
← returned: "ORD-cust-1-prod-42-3"
```

(时间会有波动——`0ms` 就是你机器上测出来的数字,和上面一样)。同一条追踪现在也进入了你已经
有的日志目的地;控制台那一行没有变。用 `structlog` 的读者可以从 `narrativetrace-structlog` 拿到
完全一样的键集合——`NarrativeContextFilter`、MDC 键和请求级别的关联,详见完整的
[日志指南](日志与structlog指南.md)。
