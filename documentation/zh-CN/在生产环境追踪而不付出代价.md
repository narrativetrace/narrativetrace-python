# 在生产环境追踪而不付出代价

## 问题

> 我想把它放到生产环境里,用于出问题的那些请求。我不想为每个顺利完成的请求
> 都付出一整条完整追踪的代价。

这只是一个设置——追踪级别——而本页就是同一次运行通过它看两遍:被拒付款的结账流程在 `DETAIL`
下,每个值都被捕获;以及在 `ERRORS` 下,只有失败的运行才会留存下来。

## 最小配置

一个级别,设置在你的部署配置所在的任何地方。下面两种写法说的是同一件事:

```toml
# narrativetrace.toml (or [tool.narrativetrace] in pyproject.toml, never both)
level = "ERRORS"   # "OFF" | "ERRORS" | "SUMMARY" | "NARRATIVE" | "DETAIL"
```

```bash
# or in the environment, which wins over the file
NARRATIVETRACE_LEVEL=ERRORS uv run pytest
```

在代码里是 `ContextVarNarrativeContext(NarrativeTraceConfig(level=TracingLevel.ERRORS))`
([配置指南,追踪级别](配置指南.md#tracing-level))。

这个级别是 NarrativeTrace 自己的旋钮,而且在最前面:被它过滤掉的调用根本不会变成事件,
对任何消费者都是如此。你的 logger 的级别是第二个独立的旋钮,决定*打印*什么——
[FAQ,“Two dials, two paths”](../faq.md#two-dials-two-paths)是详细版本,
这一区分在这里很重要,因为提高 logger 级别能节省日志量,却丝毫不改变捕获。

## 场景

这次运行是[帮我调试并修复这个缺陷](帮我调试并修复这个缺陷.md)里被拒付款的复现——
`reserve`,然后 `charge` 抛出异常,然后 `release`——原样复用,因为本页的主题是这个旋钮,
而不是另一个流程。下面的驱动程序在两个级别下都运行它,并且在两个级别下也都运行一次*成功*的结账:

```python
def _cost() -> dict[str, Run]:
    """The declined-payment reproduction at both levels, and a checkout that succeeds at both."""
    declined = "test_the_stock_is_released_when_the_card_is_declined"
    return {
        "cost_detail": _at_level("detail", "declined_payment", declined),
        "cost_errors": _at_level("errors", "declined_payment", declined, level="ERRORS"),
        "cost_detail_successful": _at_level("detail-successful", "checkout_review"),
        "cost_errors_successful": _at_level("errors-successful", "checkout_review", level="ERRORS"),
    }


def _at_level(directory: str, module: str, test: str | None = None, level: str = "DETAIL") -> Run:
    """One fixture run into its own directory, at ``level`` (the default level is DETAIL)."""
    return _run_fixture(module, _settings(COST, directory, NARRATIVETRACE_LEVEL=level), test)
```

每次调用都是一个真实的 pytest 进程,加载了 `narrativetrace-pytest`,在各自独立的目录里,
`NARRATIVETRACE_LEVEL` 的设置方式与部署时的设置方式一样。

所以这种空是级别的作用,而不是一条本来就从未走对的路径。

## 如何阅读

- **`ERRORS` 保留什么。** 失败的运行,完整保留。`#1` 抛出了异常,而错误节点的子树被完整保留——
  所以 `reserve`(`#1.1`)、`charge`(`#1.2`)和 `release`(`#1.3`)全都还在,
  包括那两次正常返回的调用。这是有意为之:失败周围的调用正是你诊断它所需要的,
  丢掉成功的兄弟调用,留给你的就只有一个异常而没有故事。一次调用如果返回了*并且*它下面
  任何地方都没有导致失败,就会被丢弃;一个整棵子树里都没有失败的根会被整个丢弃——
  这就是为什么成功的结账什么也没写。
- **`ERRORS` 丢弃什么。** 每一个参数值:`DETAIL` 在代码 span 里打印 `customer_id: "C-1234"`,
  `ERRORS` 打印 `customer_id:` 和一个空的代码 span。这个值从未被渲染,
  所以事后无法从这些事件中恢复,在任何更晚的级别下也不行。留存下来的是形状、结果
  (`reserve` 和 `release` 仍然写着 `→ null`)和异常,而 `card_number` 仍然显示
  `[REDACTED]`,因为脱敏与抑制是不同的决定。
- **裁剪发生在捕获之后,而不是代替捕获。** 每次调用都被拦截了,每个事件都被发布了;
  然后树被构建出来,级别不保留的部分被移除。这就是成本的如实形状:
  `ERRORS` 比 `DETAIL` 便宜,是因为值没有被渲染——那才是昂贵的部分——
  而不是因为调用没有被拦截。
- **只有 `OFF` 会跳过拦截。** 在 `OFF` 下,wrapper 对 `context.is_active()` 的检查在任何捕获、
  事件或发布发生之前就返回了,下游没有任何东西能把这次调用找回来——
  本仓库有一个测试断言,`OFF` 下的调用会让捕获的追踪保持为空。`ERRORS`、`SUMMARY` 和
  `NARRATIVE` 仍然会拦截每一次调用。如果问题是“在这个热点循环里追踪要花多少”,
  答案是给那个作用域用另一个级别,或者 `OFF`。
- **数字。** 没有可引用的数字,本页也不写任何数字:[README 的 Performance 一节](../../README.md#performance)
  说明了基准测试套件测量什么,以及目前尚未发布任何官方数据,有朝一日出现数据时,
  它就会出现在那里。一份随测量结果更新的副本,胜过两份互相矛盾的。

## 没有捕获的内容

- **没有可以依赖的已发布数据。** 请测量你打算运行的那个级别:你的解释器、你的硬件、
  你的参数形态(一个很深的对象图渲染起来比一个 `int` 久),以及你有多少代码被追踪,
  都会改变答案。
- **级别不是隐私控制。** `ERRORS` 恰好写出更少的值,是因为它抑制了它们,但抑制与脱敏是
  不同的机制,保证也不同:[别让密钥进日志](别让密钥进日志.md)才是在每个级别下都成立的那个。
- **这里没有任何东西改变你的 logger 写多少。** 每个被捕获的事件仍然会提供给日志桥接,
  所以决定日志量的是 `narrativetrace` logger 自己的级别。两个旋钮。
- **级别无法追溯地提高。** 没有被捕获的值就没有了;在 `DETAIL` 下重现这次运行是唯一的回头路,
  这正是调试那篇 recipe 所做的。
- **这里没有展示按作用域设置的级别。** 本页为整个运行设置一个级别。反过来收窄被追踪的作用域——
  到底包装哪些对象——是成本问题的另一半,属于[选择集成方式](选择集成方式.md)。

**对应的技能:** `narrativetrace-doctor`——它会报告项目实际运行在哪个级别,
这是追踪比预期更单薄时要检查的第一件事。
