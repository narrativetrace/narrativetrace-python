# 应提交的内容

NarrativeTrace 如今写出的所有内容都是**描述单次运行的生成产物**——这个实现 目前还没有经过审阅的
基线文件(Java 姊妹项目的结构化 `.nt` 格式及其 approval testing 工作流已经规划,但尚未在这里发布——见
[功能指南](功能指南.md))。在它落地之前,规则很简单:你配置的输出目录下的任何内容都不是源代码,
因此都不属于版本控制。

| 产物 | 路径模式 | 是否提交? | 原因 |
|---|---|---|---|
| 追踪文件(Markdown,默认格式) | `<OUTPUT_DIR>/traces/<Class>/<slug>.md` | 否 | 每次运行都会重新生成 |
| 追踪文件(`text`/`mermaid`/`plantuml` 格式) | `<OUTPUT_DIR>/traces/<Class>/<slug>.{txt,mmd,puml}` | 否 | 每次运行都会重新生成 |
| JSON 场景文档(仅 Markdown 格式) | `<OUTPUT_DIR>/traces/<Class>/<slug>.json` | 否 | 与规范 JSON 是同一个追踪——每次运行都会重新生成 |
| Mermaid 图表附件(仅 Markdown 格式) | `<OUTPUT_DIR>/diagrams/<Class>/<slug>.mmd` | 否 | 每次运行都会重新生成 |
| 规范条目数组 | `<OUTPUT_DIR>/traces/<Class>/<slug>.canonical.json` | 否 | 供一致性校验/其他实现使用的机器产物,通过 `NARRATIVETRACE_CANONICAL` 按需开启 |
| 套件清晰度报告 | `<OUTPUT_DIR>/clarity-report.md` | 否 | 生成的报告,不是决策 |
| 套件清晰度结果 | `<OUTPUT_DIR>/clarity-results.json` | 否 | 与报告一同生成 |
| 独立扫描器输出(`narrativetrace-clarity` CLI) | `--output-dir` 指向的任意位置 | 否 | 与上面相同,按需生成 |
| `glossary.json` / `glossary.md` | 仓库根目录(或你通过 `NARRATIVETRACE_GLOSSARY_DIR` 指向的位置) | **是**,如果你使用它 | 人工维护的词汇表——提交的文件就是清晰度评分读取的内容,并且从不会被测试运行重新生成。"一个文件,一个评审流程" |

默认的 `<OUTPUT_DIR>` 是 `narrative-traces`(相对于套件运行时所在的目录);把它加入项目的
`.gitignore`:

```gitignore
narrative-traces/
```

如果你把 `NARRATIVETRACE_OUTPUT_DIR` 指向别处——一个 `build/` 目录、一个 CI 产物文件夹——就改为
忽略那个路径。`glossary.json` 是唯一的例外:它存放在你放置的位置(通常是仓库根目录),从不会被
测试运行写入,应当像任何其他源文件一样被纳入版本控制。

## 一句话总结这条规则

如果一个文件的存在仅仅是因为跑了一次测试,那它就是输出——不要提交它。`glossary.json` 是这份清单
中唯一一个由人编写、而运行只会*读取*的文件——这正是它成为唯一例外的原因。

## approval testing 落地后会有什么变化

Java 姊妹项目的 `.approved.nt` / `.received.nt` 文件属于一个真正不同的类别——经人工审阅的结构化
基线是一项决策,而不是输出,应当像快照测试的 golden file 一样纳入版本控制。这个实现 目前还没有
这种机制;等它就绪后,本页会获得 Java 文档中同样的两分类划分(已审阅的基线:提交;其余一切:不提交),
而不是从头重写。
