# 隐私与脱敏

这个库运行在你的进程内部,并会写出你的团队将会分享的文件——CI 产物、生产环境日志行。本页是那份
契约逐行对照的版本:什么会被脱敏、脱敏能触达和不能触达的边界在哪里,以及 NarrativeTrace 保证
什么、又完全不承诺什么。直接对照
`packages/narrativetrace/src/narrativetrace/redaction.py` 和 `template.py` 验证得出,而不是从
其他文档推断而来。

## 脱敏,按接触面逐一说明

| 接触面 | 能否关闭内置的脱敏? |
|---|---|
| pytest 插件的输出 | 不能 |
| ASGI 中间件(请求/用户元数据导出) | 不能 |
| OpenTelemetry 桥接 | 不能 |
| structlog 处理器 / 标准库 logging 桥接 | 不能 |
| 你自己代码构造的自定义 `ValueRenderer` | 能——只能通过显式传入 `RedactionPolicy.DISABLED` 实现:`trace_object(obj, context, renderer=ValueRenderer(redaction_policy=RedactionPolicy.DISABLED))` |
| `@not_traced` / `not_traced_field(...)` | 不适用——它本身就是执行脱敏的机制,并且始终优先 |

每一个随附发布的集成都通过与 `trace_object` 默认使用的同一套 `ValueRenderer`/`RedactionPolicy`
机制渲染值(`RedactionPolicy.DEFAULT`)——它们都不会暴露任何能到达 `DISABLED` 的配置开关、环境
变量或插件设置。唯一能到达那里的方式,是应用代码自己构造一个 `ValueRenderer` 并显式传入它——这
是你自己源码中一次刻意的、可评审的行为,而不是一次部署就能悄悄切换的状态。

## 拒绝列表能捕获什么,又有什么能凌驾于它之上

两套独立的脱敏机制作用于每一个通过反射渲染的值:

1. **`@not_traced("param")` / `not_traced_field(...)` / `__nt_not_traced__`** —— 始终无条件脱敏,
   与策略无关。
2. **基于名称的拒绝列表**(`RedactionPolicy.DEFAULT`)—— 对字段/参数名做不区分大小写、不区分重音
   符号的子串匹配,**多语言且始终启用,没有可选的语言区域**:英语词汇(`password`、`secret`、
   `token`、`cvv`、`ssn`、`apikey`、`cardnumber`、`sessionid`、`passphrase`、`otp`、`bearer`
   等等)与西班牙语、葡萄牙语、法语、德语、中文词汇(`contraseña`、`senha`、`motDePasse`、
   `passwort`、`密码` 等等)并列——`pan`/`iban` 以及八个非英语词
   按标识符 token 边界匹配,而不是作为原始子串匹配,专门是为了不让 `companyName` 或
   `japaneseAddress` 被误伤——再加上第二个独立的检查,针对值本身的*形状*:JWT、`Set-Cookie`
   字符串、形似卡号的数字串,或是通过了自身校验位或结构规则的国民身份证号(智利 RUT、巴西
   CPF/CNPJ、西班牙 DNI/NIE、法国 NIR、中国居民身份证、美国社会安全号 SSN)——美国 SSN 没有
   校验位,所以由 SSA 从未发放过的地区/组/序列号来承担这个作用——因此一个以未识别名称传递的
   bearer token 或身份证号依然会被捕获。

`NamedTuple` 是按字段名内省的,而不是渲染成一个匿名的位置元组,因此其内部一个被脱敏的字段会像
dataclass 字段一样保持隐藏——脱敏能在容器内多穿透一层依然生效。而且它会凌驾于引用它的叙述模板
之上:`@narrated`/`@on_error` 中的 `{param.property}` 在解析到一个已脱敏成员的路径时,会得到
`[REDACTED]`,在路径的每一层深度都是如此,永远不会是字面值。

**复合类型自身的 `__str__`/`__repr__` 永远不被信任** *(since 0.1.2, unreleased)*。任何携带实例状态的对象——
dataclass、attrs 类、`NamedTuple`,或者拥有非空 `__dict__`/`__slots__` 的普通对象——都会被逐字段
内省,无论它是否还定义了自定义的 `__str__`/`__repr__`;那个手写的方法永远不会被这类对象采纳。
修复之前,`ValueRenderer` 只要一个普通类重写了默认的 `__str__` 就会直接信任它,于是一个手写的、
会插入敏感字段的 `__str__`——无论是直接插入,还是通过一个嵌套对象自身的 `__str__` 间接插入——
都会完全不经中介地到达输出,绕过拒绝列表、深度上限,绕过一切。dict/map 的键存在完全相同的漏洞:
过去它只是裸露、未经中介的 `str(key)`,因此一个被用作键的敏感对象会无条件泄露,无论它的值里有
什么。现在两者都会像普通值一样被内省并接受脱敏检查——只有真正的叶子值(完全没有实例状态:数字、
字符串、无状态的辅助类、没有携带数据的 `Enum` 成员)才仍然信任自己的 `str()`。`@narrative_summary`
不受影响,依然是让复合类型给出一行精心编排摘要、而不是逐字段默认渲染的受支持方式。

当 `@narrative_summary` 方法、自定义 `__str__`,或者字段自身的 getter 抛出异常时 *(since 0.1.2,
unreleased)*,那一部分会渲染成
`<error: <TypeName>>`——只为那一部分替换成异常自身的类型名(`<error: ValueError>`、
`<error: RecursionError>`)。异常的*消息*被刻意地永远不渲染,因为消息里可能带着那个渲染失败的值
本身;只有类型名会到达输出,绝不会是 `str(exc)`。

**一处已记录、而非已修复的局限。** 模板占位符解析(`{param}`、`{param.property}`)始终针对
`RedactionPolicy.DEFAULT` 检查值——这个策略不会从你传给 `trace_object` 的自定义 `ValueRenderer`
中被传递过去。实际上这只在你同时构造了一个自定义或已禁用的策略时才有影响:普通的参数和返回值
渲染会遵循那个自定义策略,但一个解析同一个值的 `@narrated`/`@on_error` 模板,底层依然会检查默认
拒绝列表。`@not_traced` 不受影响——无论当前生效的是哪种策略,它始终脱敏。

完整细节与实战示例见[装饰器指南](装饰器指南.md)。

## 保证

- **追踪失败与宿主执行相互隔离。** 记录在每一条路径上都做了异常隔离;一个抛出异常的 `__str__`、
  一个已满的缓冲区,或一个损坏的日志处理器,永远不会改变你的方法返回或抛出的内容。
- **输出无法被伪造。** 渲染出的值、异常消息和叙述文本,在到达一条日志行、一个控制台渲染器或
  一份 Markdown 文档之前,都会经过控制字符和代理项(surrogate)转义——因此一个值无法注入一条
  伪造的日志行,也无法破坏产物的格式。
- **缓冲分析路径可能丢弃事件,但始终会报告丢失。** 它是一个固定大小的环(默认 65,536 个槽位——
  面向自行搭建管道的代码,这是 `BufferedEventConsumer` 构造函数的 `buffer_capacity` 参数),在
  持续高负载下会覆盖最旧的事件,而不是无限增长或阻塞调用方;一次丢失了事件的运行,会在自己的
  套件页脚 `Incomplete:` 那一行打印丢失数量,而不是悄悄少报。
- **内省读取的是已存储的数据,而不是代码。** 字段名来自 `dataclasses.fields()`、attrs 的元数据、
  `NamedTuple` 的 `_fields`,或者实例的 `__dict__`/`__slots__`——一个计算型的 `@property` getter
  永远不会在内省过程中被枚举,也永远不会被执行。

## 非保证

- **不承诺“零开销”。** 追踪确实要做工作,而工作总会消耗一些成本——见
  [自述文件的性能一节](../../自述文件.md#性能)。
- **不追踪私有方法。** `trace_object` 只拦截公共属性访问(`__getattr__`);一个以 `_` 开头的名字
  永远不会被包装,dunder 方法(`__str__`、`__eq__` 等)也是在类型上解析的,同样永远不会到达
  wrapper——因此一个被包装对象的 `str()`/`repr()`/`==`/`isinstance()` 会悄悄地不再反映原始对象,
  且没有任何标记或反包装 API 可以从外部检测到这次包装。
- **不会自动追踪一个你没有显式包装的对象。** 目前没有 import hook,没有字节码插桩,也没有随框架
  提供的全局自动包装——见[选择集成方式](选择集成方式.md)。
- **测试名称不会被脱敏。** 测试的显示名称——包括 `@pytest.mark.parametrize` 的 id
  (`test_finds_it[KAYAK]`)——是开发者编写或由运行器生成的标识文本,而不是被捕获的值:它会原样
  (经过人性化处理,但从不脱敏)出现在 `narrativetrace-pytest` 产物的 `scenario:`/`**Scenario:**`
  头部以及文件名中。不会为它查询任何拒绝列表,这是刻意如此(跨运行时的结构化头部约定):这个库
  目前还没有提供无值的结构化产物——[功能指南](功能指南.md)明确说明:“pytest 插件为每个测试写出
  一个包含全部细节的文件”——因此它每个测试唯一的产物就是携带值的那种,自然会在任何地方保留显示
  名称。请像对待 `@narrated`/`@on_error` 模板一样,不要把敏感信息放进 `parametrize` 的 id 里。

## 生产环境中的丢失模型,直观呈现

双路径管道(产品决策记录 PY-002)的两半,在设计上承担着相反的义务:

```text
同步日志路径(标准库 logging,内联在调用方线程上)
   绝不能让宿主应用失败
   持久——这才是记录

缓冲分析路径(有边界的环,由一个后台线程排空)
   可能在高负载下丢弃事件,并且始终会说明这一点
   绝不能阻塞调用方
   绝不能超出其边界增长(默认 65,536 个槽位)
   尽力而为——这是分析,不是审计
```

丢失缓冲区会丢失分析的保真度——被捕获的树、清晰度评分、OTel span——针对那个窗口期内被丢弃的
事件。丢失日志流会丢失记录本身。正是这种不对称性,决定了它们是两条具有两种不同失败行为的路径,
而不是一条路径搭配单一的权衡取舍。

## 本页未覆盖的内容

当 NarrativeTrace 与 AOP 风格的代理、契约库,或另一个包装同一对象的工具叠加使用时会发生什么,
遵循两条不变式——每次跨越业务边界只产生一个追踪帧,且没有任何结果依赖于 wrapper 的叠加顺序——
这部分内容收录在[自述文件的隐私与安全一节](../../自述文件.md#隐私与安全)。每一个追踪级别和输出
格式开关,包括 `NARRATIVETRACE_LEVEL` 如何在任何渲染发生之前就控制捕获,都在
[配置指南](配置指南.md)中。
