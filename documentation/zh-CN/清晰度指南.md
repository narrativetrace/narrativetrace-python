# 清晰度

因为追踪*就是*你的命名,`narrativetrace-clarity` 会客观地为命名质量评分,并可以在命名质量下降时
让 CI 失败。

## 为一条追踪评分

```python
from narrativetrace_clarity import analyze

result = analyze(context.capture_trace())
print(result.overall_score)          # 0.0(差)… 1.0(优秀)
for issue in result.issues:          # 按影响程度排序
    print(issue.severity.name, issue.category, issue.element, "→", issue.suggestion)
```

五个加权维度:方法名(0.30)、类名(0.20)、参数名(0.25)、结构(0.15)、内聚性(0.10)。评分依赖
跨实现字节级完全一致的词典:34 个领域类别下的 1053 个动词、187 个缩写、35 个搭配
映射,以及角色后缀表。

问题会按分数区间分类(HIGH ≤ 0.20,MEDIUM ≤ 0.50),按 `category|element` 去重并累加出现次数,
再按影响程度排序。

## 你自己的词汇表——来自你已经拥有的术语表

内置词典了解的是通用的软件英语。它们不知道 `fold` 在你的领域里是一个动词,不知道 `tranche` 是
一个精确的名词,也不知道 `fx` 是你的团队已经接受的缩写——一个它们不认识的名字会被评为未知,而
不是领域专属。

你要用你的仓库已经拥有的词汇表文件来教会它们:已提交的 `glossary.json`(ADR-012)。不需要维护
第二份、需要保持同步的词典文件。

| 术语表条目 | 类型 | 清晰度会学到什么 |
|---|---|---|
| `settle trade` | `verb-phrase` | `settle` 是一个领域动词;`trade` 是一个领域名词 |
| `credit tranche` | `noun-phrase` | `credit` 和 `tranche` 都是领域名词 |
| `fx` | `word` | `fx` 是一个领域名词 |

多词术语会逐个 token 学习,因为标识符本身就是逐个 token 评分的。每一个限界上下文都会做出贡献:
一个标识符不携带模块路径,因此按上下文划分作用域的做法在评分时无法应用。

### 认可的缩写是独立的一个小节

项目认可哪些缩写,是一个与领域使用哪些词汇完全独立的决定,因此它存放在 `glossary.json`
(schema 2)自己独立的根级小节里:

```json
{
  "schemaVersion": 2,
  "contexts": { "trading": { "packages": ["acme.trading"] } },
  "abbreviations": { "fx": "foreign exchange", "calc": "calculate" },
  "terms": []
}
```

列在那里的 token 永远不会被要求写出完整形式。一个仅仅*出现在*某个已提交术语内部的 token 则不会:
提交名词短语 `calc total` 会教会系统 `calc` 和 `total` 都是领域名词,但不会说明 `calc` 是否是被
认可的缩写——因此 `calc` → `calculate` 这条提示会在仓库的其余部分继续生效。

这个小节归人类所有:采集过程永远不会写入它,合并一次采集结果时也会将它原样保留。一个没有声明
任何缩写的术语表会被标记为 `"schemaVersion": 1`,并写出与该小节存在之前完全相同的字节,因此
采用这项功能不会带来任何 diff 噪音。读取方在任何 schema 版本下都能接受这个小节。

内置词典始终保有其权威性。一个项目可以教会评分器一个它们不认识的词;但不能推翻一个它们已经
认识的词——泛化动词(`process`、`handle`)和布尔前缀(`is`、`has`)依然保持原状,没有意义的
占位词(`temp`、`foo`)不会因为被写下来就被拯救,而废弃的同义词、`template` 条目以及 `stale`
术语永远不算作词汇。只有*已提交*的文件才算数:一次运行采集到的内容永远不会反馈进同一次运行的
评分中,那样会让评分变得不确定,并且自我认证。

```python
from narrativetrace_clarity import analyze
from narrativetrace_glossary import read_project_vocabulary

result = analyze(context.capture_trace(), read_project_vocabulary("."))
```

pytest 插件会在每个会话中为你自动做这件事一次:`narrativetrace.glossary_dir`(环境变量
`NARRATIVETRACE_GLOSSARY_DIR`)指定目录,默认为工作目录。读取是无条件的——它不会改变磁盘上的
任何内容——一个无法读取的术语表会降级为内置词典并给出一条警告,而不是让整个套件失败。

## CI 门禁

`narrativetrace-clarity` 控制台脚本会扫描 Python 源码(每个公共方法都是一个深度为 1 的根),
并写出 `clarity-results.json` + `clarity-report.md`:

```bash
narrativetrace-clarity src --min-score 0.5 --max-high-issues 0 --output-dir build/narrativetrace
# --format both|md|json   --warn-only   (未知格式 → 退出码 2;低于阈值 → 退出码 1)
```

在本仓库中,它通过 `clarity` 任务接入了 `uv run poe check`。

## 运行时聚合

pytest 插件会为每个测试捕获到的树评分,打印一条 `Clarity: X% high | …` 的页脚,并且(在启用输出
时)为每个被追踪的测试聚合一条 `clarity-results.json` 记录。
